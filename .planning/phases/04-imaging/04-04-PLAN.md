### The two new build tasks

```
./build.ps1 -Task integration    # tests/integration - real DISM, real VHDX, requires elevation
./build.ps1 -Task e2e            # tests/e2e        - Hyper-V, requires elevation
```

Neither is part of `ci`, and `-Task ci` stays exactly the five it composes today
(DESIGN 12.2.5 puts integration on pushes to `main` and E2E nightly; wiring that
into CI is M4's problem, and this host is not CI). Each throws a sentence naming
the missing precondition - elevation, Hyper-V, the staged media - rather than
failing obscurely inside a test.

**The dispatcher has a trap in it, and adding to the `ValidateSet` alone walks
straight into it.** `build.ps1` ends with

```powershell
$canonicalOrder = @('clean', 'build', 'lint', 'test', 'selfcheck')
$ordered = @($canonicalOrder | Where-Object { $requested -contains $_ })
```

so a task that is accepted by the `ValidateSet` but absent from `$canonicalOrder`
produces an **empty** `$ordered`: the `foreach` runs nothing, the script prints
`BUILD SUCCEEDED ()` and **exits 0**. `./build.ps1 -Task integration` would then
"pass" without having run a single integration test, and this plan's own
verification step would report success for a suite that never executed. The two
new tasks must therefore be added to the ordered dispatch as well as to the
`ValidateSet`, and `$ordered` being empty must be a **failure**, not a success.

`tests/unit/BuildScript.Tests.ps1` asserts, by parsing `build.ps1`: the
`ValidateSet` contains `integration` and `e2e`; `ci` expands to the five
canonical tasks and **not** to those two; and `Invoke-HDTTest`'s `Run.Path`
still names only `tests/unit` and `tests/contract`. Without that test the first
person to add `tests/integration` to the default path turns a two-second suite
into a twenty-minute one that needs a disk.

### The lab helpers

```
New-HDTLabScratchDisk -Path <string> -SizeByte <long> [-Dynamic]  -> @{ DiskNumber; Path }
Remove-HDTLabScratchDisk -Path <string>

New-HDTLabVirtualMachine -Name <string> -MemoryByte <long> -ProcessorCount <int>
                         -SwitchName <string> -VhdPath <string[]> -IsoPath <string>
Remove-HDTLabVirtualMachine -Name <string> [-KeepFile]
New-HDTLabContentDisk -Path <string> -SizeByte <long> -Source <hashtable>
Send-HDTLabVmText -Name <string> -Text <string> [-Enter]
Save-HDTLabVmScreen -Name <string> -Path <string>
Wait-HDTLabVmState -Name <string> -State <string> -TimeoutMinute <int>
Wait-HDTLabVmState -Name <string> -Heartbeat -TimeoutMinute <int>
Get-HDTLabOfflineComputerName -VhdPath <string>
```

- `New-HDTLabScratchDisk` refuses to return a disk that is `IsBoot` or
  `IsSystem`, so an integration test cannot be handed the developer's disk even
  if the mount misbehaves.
- `Send-HDTLabVmText` is SPIKES S4's `Msvm_Keyboard` `TypeText` / `TypeKey`,
  filtered by `SystemName = <the VM's Msvm_ComputerSystem.Name GUID>`, not its
  `ElementName`.
- `Wait-HDTLabVmState -Heartbeat` waits for the integration-services heartbeat to
  report `Ok*`. **WinPE has no integration services and never reports one, and
  full Windows does** — so the heartbeat is a deterministic "the machine booted
  into Windows" signal, and it is a far better assertion than reading pixels.
  `Save-HDTLabVmScreen` still writes a screenshot for a human to look at, which
  is diagnosis, not assertion.
- `Get-HDTLabOfflineComputerName` mounts a VHDX read-only, `reg load`s
  `SYSTEM\ControlSet001\Control\ComputerName\ComputerName`, reads it and
  **unloads in a `finally`**, exactly as SPIKES S8 did. That is how the unattend
  is proven to have applied.

### The E2E topology, and why it looks like this

```
VM  HDT-M3-Deploy   Gen2, Secure Boot on, 4 GB, 2 vCPU, switch 'HDT Lab',
                    files under C:\HDTLab\vms\HDT-M3-Deploy\
  DVD    C:\HDTLab\scratch\pe\HDTPE_x64_uefi.iso        (SPIKES S1/S3's image)
  Disk 0 HDT-M3-Deploy-osdisk.vhdx    64 GB dynamic      the deployment target
  Disk 1 HDT-M3-Deploy-content.vhdx    8 GB dynamic      the workspace and the engine
```

**Why content on a disk rather than a share.** PROJECT.md requires the isolated
`HDT Lab` switch, and SPIKES S6 records that a VM on an isolated switch cannot
reach a share on the host — S6 used an External switch to get around it, which
the lab rules do not allow for a routine test. A locally attached content disk
removes SMB, DHCP and the host firewall from the exit criterion entirely, so a
failure means *the imaging code* failed. It is also DESIGN 6.2's `Local`
provider shape, one milestone early.

**Why 8 GB of content and 60 GB of minimum.** `DEMO-M3` declares
`minDiskGB: 60`, so the content disk is excluded from candidacy by size and the
target is unambiguous — the automatic selection path, not the `diskNumber`
override. `DiskPartition` *also* protects the content disk by drive letter, so
two independent rules stand between the engine and the workspace it is reading.

Content disk layout:

```
<content>:\HDT\Modules\Hephaestus\        the module, copied from src/
<content>:\HDT\Modules\powershell-yaml\   the parser the engine needs
<content>:\HDT\Start-HDTLabDeployment.ps1 the launcher
<content>:\Share\rules.yaml
<content>:\Share\TaskSequences\DEMO-M3\sequence.yaml, unattend.xml
<content>:\Share\OperatingSystems\Win11-LTSC-2024\os.yaml
<content>:\Share\OperatingSystems\Win11-LTSC-2024\sources\install.wim
<content>:\Share\Logs\
```

Every path under `Share\` is built with `Get-HDTWorkspacePath` by the code that
reads it; the harness that *stages* it writes the same layout by hand and a test
asserts the two agree.

### `Start-HDTLabDeployment.ps1` — what it may and may not do

It is the phase-04 stand-in for phase 05's `Start-HDTDeployment.ps1`, lives under
`tests/e2e/payload/`, and does exactly six things:

1. Adds `<its own drive>\HDT\Modules` to `PSModulePath` and imports `Hephaestus`
   and `powershell-yaml`, **logging the version of each** — this is the WinPE
   dependency proof.
2. Builds the real adapters: `New-HDTFileSystem`, `New-HDTClock`,
   `New-HDTDiskService`, `New-HDTImageService`, `New-HDTRegistryService`,
   `New-HDTEnvironmentProvider`, `New-HDTCimProvider`, `New-HDTProcessService`,
   `New-HDTPowerService`, `New-HDTScriptInvoker`, and a `New-HDTServiceCatalog`.
3. `Get-HDTMachineFact` → `Resolve-HDTVariable` against `Share\rules.yaml` and
   the sequence defaults.
4. `New-HDTLogContext` (`X:\HDT\Logs`), `New-HDTRunState`,
   `New-HDTExecutionContext`, `Import-HDTSequenceDocument`.
5. **One** call to `Invoke-HDTTaskSequence`, with `-LogDestination` pointing at
   `Share\Logs\<computer>-<runId>` so the whole log survives on the content disk.
6. Writes `Share\Logs\<computer>-<runId>\RESULT.json` (status, failed step,
   engine version, elapsed) and shuts the machine down with `wpeutil shutdown`,
   which is how the harness knows the run ended.

**It contains no deployment logic.** `tests/unit/StartHDTLabDeploymentPayload.Tests.ps1`
asserts that by parsing it, exactly as 03-04 asserts `Start-HDTResume.ps1`: it
parses under both engines, passes the 5.1 syntax scanner, defines no unprefixed
function, names no `New-HDTFake*`, names **no** Storage cmdlet, DISM cmdlet,
`bcdboot`, `bcdedit`, `reagentc` or `diskpart`, and calls
`Invoke-HDTTaskSequence` exactly once. A launcher that partitioned a disk itself
would make the exit criterion a lie.

### Starting it inside WinPE

The boot image's `startnet.cmd` launches nothing of HDT's (it predates the
engine), so the harness types one line at the WinPE prompt with
`Send-HDTLabVmText` (SPIKES S4), scanning for the content drive because WinPE's
letter assignment is not guaranteed:

```
for %d in (C D E F G) do @if exist %d:\HDT\Start-HDTLabDeployment.ps1 powershell -ep bypass -f %d:\HDT\Start-HDTLabDeployment.ps1
```

Wiring the engine into `startnet.cmd` is M4's job (`Update-HDTBootImage`); typing
one line is the smallest thing that does not pretend otherwise.

### The WinPE smoke check — run it before the deployment, deliberately

A single short run that de-risks the deployment and closes the repository's one
derived fixture. Build a small content disk with the module, `powershell-yaml`
and a probe script; boot `HDT-M3-Smoke` (Gen2, 2 GB, `HDT Lab`, the PE ISO,
**one** small VHDX so nothing can be mistaken for a target); type the launcher
line; let the probe write to the content disk and shut down; mount the disk on
the host and read the result.

**`HDT-M3-Smoke` is created and removed by the same helpers and the same rules as
the deployment VM**, and its removal is in a `finally` so an aborted probe does
not leave a second VM behind - `<lab_safety>` rule 6 applies to it exactly as it
does to `HDT-M3-Deploy`, and the memory budget is checked before it starts.

The probe records, and the summary must report, all four:

1. `$PSVersionTable.PSVersion` inside WinPE.
2. Whether `Import-Module powershell-yaml` **succeeds in WinPE**, and its
   version. *If it does not, the engine cannot read a sequence in WinPE and this
   is the most important finding of the phase.* Record it in SPIKES.md - and
   then **fix it here, in 04-04, before task 3 runs**. It is not deferrable:
   `Import-HDTSequenceDocument` goes through `ConvertFrom-HDTYaml`, so a WinPE
   that cannot load the parser cannot run a sequence, and M3's exit criterion is
   "a VM boots into Windows **from a sequence run**". A phase that hands this to
   phase 05 does not meet its own goal.

   The fix ladder, cheapest first, and each rung is recorded in the summary
   whether or not it was needed:

   a. `WinPE-NetFx` is present (SPIKES S1) but the module may fail to resolve its
      own `lib
et47` path from a non-standard root - stage it under a directory
      on `PSModulePath` and `Add-Type -Path` the two DLLs before importing.
   b. Force the `net47` flavour explicitly rather than letting the module choose.
   c. If the assembly genuinely will not load, `ConvertFrom-HDTYaml` is the one
      place in the engine that names `ConvertFrom-Yaml`, so the seam already
      exists - and the amount of YAML the WinPE leg reads is small.

   Whatever it takes, the summary states which rung was used, and SPIKES gets the
   finding either way.
3. Whether `Get-HDTMachineFact` succeeds in WinPE against the real CIM provider,
   registry and environment, and the fact set it produced — the first time
   phase 02's gatherer runs in its actual home.
4. `Get-Disk` projected exactly as `tests/fixtures/disk/host-nvme-disk.json` is,
   written to the content disk as JSON.
5. Whether **`Import-HDTSequenceDocument` parses the real `DEMO-M3` sequence** in
   WinPE, and `Import-HDTRuleDocument` the real `rules.yaml`. Importing the
   parser module is necessary but not sufficient - the thing task 3 depends on is
   a sequence document actually coming back, and proving that costs the probe two
   more lines.

Then **replace `tests/fixtures/disk/gen2-vm-raw-disk.json` with that capture**,

### What the test does, in order

`BeforeAll`
1. Record `CM01` and `DC01` state, memory and switch. Assert the total assigned
   memory of running `HDT-*` VMs is under 12 GB.
2. Build the content disk with `New-HDTLabContentDisk`: the module from `src/`,
   `powershell-yaml`, the launcher, and the workspace — `rules.yaml`,
   `TaskSequences\DEMO-M3\` (the **sample files, copied, not retyped**),
   `OperatingSystems\Win11-LTSC-2024\os.yaml` and
   `sources\install.wim` copied from the staged media (~4 GB, a couple of
   minutes).
3. Create the 64 GB target VHDX and `HDT-M3-Deploy` with
   `New-HDTLabVirtualMachine`: Gen2, Secure Boot on, 4 GB, 2 vCPU, `HDT Lab`,
   `C:\HDTLab\vms\HDT-M3-Deploy\`, the PE ISO in the DVD drive, DVD first in the
   boot order.
4. Start it, wait for the WinPE prompt (a fixed settle of ~120 s — SPIKES S1
   measured under 100 s — plus a screenshot saved for the record), then
   `Send-HDTLabVmText` the launcher line with `-Enter`.
5. `Wait-HDTLabVmState -State Off -TimeoutMinute 45` — the launcher shuts the
   machine down when the sequence ends, whatever the outcome.
6. Mount the content VHDX read-only on the host and read `RESULT.json`,
   `HDT.jsonl` and `state.json`; dismount.

`Context 'it boots into Windows'` — **the exit criterion**
- `It 'boots into Windows with the installation media still attached'` — start
  the VM **without touching the boot order or ejecting the ISO**, and
  `Wait-HDTLabVmState -Heartbeat -TimeoutMinute 20`. This is SPIKES S6's fourth
  finding, inverted: a machine that boots WinPE again fails here, and that means
  `ConfigureBoot` did not do its job
- `It 'reports an Ok heartbeat'` — full Windows, which WinPE never reports
- `It 'saved a screenshot of the running machine'` — the artifact a human reads,
  written under `C:\HDTLab\scratch\e2e\`
- `It 'applied the computer name from the unattend'` - **settle first, then stop
  gracefully.** `ComputerName` is applied in the `specialize` pass and the
  heartbeat can appear while Setup is still working, so a VM stopped at the first
  `Ok*` may not have committed it yet, and the test would fail for a reason that
  has nothing to do with HDT. Wait for the heartbeat, then wait for it to stay
  `Ok*` across a settle window (a few minutes), then `Hyper-V\Stop-VM -Name
  'HDT-M3-Deploy'` **gracefully** through integration services - falling back to
  `-TurnOff` only after a timeout, and recording in the summary that it did.
  Then mount the target VHDX and `Get-HDTLabOfflineComputerName`, comparing with
  `HDTComputerName` from the sequence. SPIKES S7's specialize behaviour, now
  driven by the engine. If the name is still the Setup-generated one, that is a
  timing finding for SPIKES, not a licence to loosen the assertion

`Context 'the lab is unharmed'`
- `It 'left CM01 in the state it found it'` — state, memory, switch
- `It 'left DC01 in the state it found it'`
- `It 'left every HDT VM powered off'`
- `It 'touched no VM outside HDT-*'` — assert from the transcript of the run

### If the boot-order assertion fails

Do not "fix" it by ejecting the ISO from the host. Record what happened in
SPIKES.md, use `Hyper-V\Set-VMFirmware` **once, as a diagnostic**, to learn
whether the machine boots when the media is demoted, and report the result as a
gap in `ConfigureBoot` with the evidence. A phase that quietly removed the DVD
would ship a toolkit that loops back into WinPE on every real deployment, and
SPIKES S6 wrote that trap down precisely so it would not be papered over.
