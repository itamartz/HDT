### IDiskService — nine methods, three of them read-only

```
GetDisk()      -> [object[]]  every disk on the machine
GetPartition() -> [object[]]  every partition on every disk
GetVolume()    -> [object[]]  every volume with a drive letter

ClearDisk([int] $DiskNumber)                                  -> void
InitializeDisk([int] $DiskNumber, [string] $PartitionStyle)   -> void
NewPartition([int] $DiskNumber, [long] $SizeByte, [bool] $UseMaximumSize,
             [string] $GptType, [bool] $IsActive)             -> the created partition row
SetPartitionDriveLetter([int] $DiskNumber, [int] $PartitionNumber, [string] $DriveLetter) -> void
SetPartitionType([int] $DiskNumber, [int] $PartitionNumber, [string] $GptType)            -> void
FormatVolume([string] $DriveLetter, [string] $FileSystem, [string] $Label)                -> void
```

**Three flat listings, no filters and no joins** — the same decision
`ICimProvider` made when it refused a `-Filter`. A partition row carries its
`DiskNumber` and a volume row carries its `DriveLetter`, so *the pure logic in
04-02 does the joining* and the adapter stays a projection of three cmdlets.
An adapter that filtered would be an adapter with a branch in it.

Row shapes, fixed here because 04-02 and 04-03 assert on them:

| `GetDisk()` | Meaning |
|---|---|
| `Number` | `[int]` |
| `FriendlyName` | `[string]` |
| `SerialNumber` | `[string]`, sanitised in fixtures |
| `SizeBytes` | `[long]` — `Get-Disk`'s `Size` |
| `BusType` | `[string]` — `NVMe`, `SAS`, `USB`, `File Backed Virtual`, … |
| `PartitionStyle` | `[string]` — `RAW`, `MBR`, `GPT` |
| `IsBoot` / `IsSystem` / `IsReadOnly` / `IsOffline` | `[bool]` |
| `OperationalStatus` | `[string]` |

| `GetPartition()` | Meaning |
|---|---|
| `DiskNumber` / `PartitionNumber` | `[int]` |
| `DriveLetter` | `[string]`, empty when none |
| `SizeBytes` / `OffsetBytes` | `[long]` |
| `Type` | `[string]` — `Basic`, `System`, `Reserved`, `Recovery`, … |
| `GptType` | `[string]`, empty on MBR |
| `IsActive` / `IsHidden` / `IsBoot` / `IsSystem` | `[bool]` |

| `GetVolume()` | Meaning |
|---|---|
| `DriveLetter` | `[string]` |
| `FileSystem` | `[string]`, empty for RAW |
| `FileSystemLabel` | `[string]` |
| `SizeBytes` / `SizeRemainingBytes` | `[long]` |

`NewPartition` returns the row it created, with the `PartitionNumber` the system
assigned. `UseMaximumSize = $true` means `SizeByte` is ignored. An empty
`$GptType` means "do not pass `-GptType`" and an empty `$DriveLetter` means
"remove the access path".

**The one behaviour that must be modelled, not documented (SPIKES S6):**
`Initialize-Disk -PartitionStyle GPT` **silently creates a 16 MB MSR of its
own.** HDT never creates one. The fake reproduces this — `InitializeDisk` with
`GPT` adds a `Reserved` partition to its own state — so a step that "helpfully"
creates an MSR produces a **duplicate** the tests can see. A fake that did not
model it would let the exact bug the spike found back into the codebase.

### IImageService — five methods

```
GetImageInfo([string] $ImagePath) -> [object[]]  Index, Name, Description, Edition,
                                                 SizeBytes, Architecture, Version
ApplyImage([string] $ImagePath, [int] $Index, [string] $ApplyPath)               -> void
InstallBootFile([string] $OsRoot, [string] $SystemVolume, [string] $Firmware)    -> void
SetRecoveryImage([string] $OsRoot, [string] $RecoveryPath)                       -> void
SetBootOrderFirst()                                                             -> void
```

The real adapter, and the exact native mechanism each wraps:

| Method | Mechanism |
|---|---|
| `GetImageInfo` | `Get-WindowsImage -ImagePath $p`, then `Get-WindowsImage -ImagePath $p -Index $i` per index for `EditionId` / `Version` / `Architecture`. A `foreach` over the indices, no `if` |
| `ApplyImage` | `Expand-WindowsImage -ImagePath $p -Index $i -ApplyPath $root` (DESIGN 9.2) |
| `InstallBootFile` | `bcdboot.exe "<OsRoot>\Windows" /s <SystemVolume> /f <UEFI\|BIOS\|ALL>` |
| `SetRecoveryImage` | `reagentc.exe /setosimage /path <RecoveryPath> /target <OsRoot>\Windows` |
| `SetBootOrderFirst` | `bcdedit.exe /set "{fwbootmgr}" displayorder "{bootmgr}" /addfirst` |

`SetBootOrderFirst` is **SPIKES S6's fourth finding as an API**: after apply, a
machine that still has the boot media first in the firmware order simply reboots
into WinPE. `ConfigureBoot` (04-03) owns calling it; this plan owns making it
callable.

Each native call checks `$LASTEXITCODE` and throws with the tool's own output
attached. That is the *whole* of the allowed logic: DESIGN 12.2.3's "adapters
stay dumb — just argument construction and exit-code checking".

### Both adapters are pscustomobjects, and both record

tests/helpers/README.md F1: a real adapter is a `[pscustomobject]` with
`ScriptMethod` members, never a PowerShell class. F3: **every array-returning
`ScriptMethod` returns with the unary comma** — `return , ([object[]] @($row))` —
or a single-disk machine (this one) reports a scalar and every `.Count` in 04-02
is wrong. F10: both factories carry the
`PSUseShouldProcessForStateChangingFunctions` suppression.

Both take `-Journal`, expose `$Operations`, `GetOperationName()` and
`$ServiceName` (`DiskService`, `ImageService`), and **record before the call can
throw** (README section 4).
