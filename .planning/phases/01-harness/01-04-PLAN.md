### GREEN: .github/workflows/ci.yml

```yaml
name: CI

on:
  push:
    branches: [ main ]
  pull_request:
  workflow_dispatch:

jobs:
  windows:
    name: ${{ matrix.shell }}
    runs-on: windows-latest
    strategy:
      fail-fast: false
      matrix:
        shell: [ pwsh, powershell ]
    steps:
      - uses: actions/checkout@v4

      - name: Install build dependencies
        shell: ${{ matrix.shell }}
        run: |
          [Net.ServicePointManager]::SecurityProtocol = [Net.SecurityProtocolType]::Tls12
          Install-PackageProvider -Name NuGet -MinimumVersion 2.8.5.201 -Force | Out-Null
          Set-PSRepository -Name PSGallery -InstallationPolicy Trusted
          Install-Module Pester            -RequiredVersion 5.7.1  -Scope CurrentUser -Force -SkipPublisherCheck
          Install-Module PSScriptAnalyzer  -RequiredVersion 1.25.0 -Scope CurrentUser -Force
          Install-Module powershell-yaml   -RequiredVersion 0.4.12 -Scope CurrentUser -Force

      - name: Build, lint, test, self-check
        shell: ${{ matrix.shell }}
        run: ./build.ps1 -Task ci

      - name: Upload test results
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: pester-${{ matrix.shell }}
          path: out/testResults/*.xml
```

Notes that matter:
- `shell: powershell` on `windows-latest` **is** Windows PowerShell 5.1 — that is
  what makes the dual-engine requirement real in CI rather than aspirational.
- The TLS 1.2 + NuGet provider lines are needed for the 5.1 leg to reach PSGallery.
- `-Scope CurrentUser` installs into edition-specific module paths, so each
  matrix leg installs its own copy. Do not try to share them.
- Modules are pinned to the versions verified on the development machine so a
  gallery update cannot turn CI red without a deliberate change.
- `run:` uses `./build.ps1 -Task ci`, the same entry point developers use — CI
  must never grow its own private build logic (DESIGN §12.2.5).

The exit criterion is *"`./build.ps1 test` runs green on a clean clone under
pwsh 7 and PS 5.1"*. A clean clone contains only committed content, so this also
proves nothing required by the build is sitting untracked on this machine.

**Commit everything from tasks 1 and 2 first**, then:

```powershell
$clone = Join-Path $env:TEMP ('hdt-clean-' + [guid]::NewGuid().ToString('N'))
git clone --local . $clone
Push-Location $clone
try {
    & 'pwsh.exe'       -NoProfile -File ./build.ps1 -Task test ; $pwshTest  = $LASTEXITCODE
    & 'powershell.exe' -NoProfile -File ./build.ps1 -Task test ; $winTest   = $LASTEXITCODE
    & 'pwsh.exe'       -NoProfile -File ./build.ps1 -Task ci   ; $pwshCi    = $LASTEXITCODE
    & 'powershell.exe' -NoProfile -File ./build.ps1 -Task ci   ; $winCi     = $LASTEXITCODE
    "pwsh test=$pwshTest  win test=$winTest  pwsh ci=$pwshCi  win ci=$winCi"
} finally {
    Pop-Location
    Remove-Item -LiteralPath $clone -Recurse -Force
}
```

Required outcome: `pwsh test=0`, `win test=0`, `pwsh ci=0`. `win ci` is expected
to be **non-zero on this machine only** because `lint` throws when
PSScriptAnalyzer is unavailable to 5.1 — that is by design (see 01-01) and it is
green in CI, where the workflow installs PSSA into the 5.1 module path. Record
the actual four numbers in the SUMMARY; if `win ci` fails for any reason other
than the PSSA availability message, it is a real failure and must be fixed.

If any run is red, fix it in this plan — do not defer. The most likely causes
are: a file needed by the build not committed (check `git status --ignored`), an
absolute path baked into `build.ps1` or a test, or a test depending on module
state left behind by a previous run.
