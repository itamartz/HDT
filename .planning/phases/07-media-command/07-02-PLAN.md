<objective>
Build the disc. `Update-HDTMediaContent` takes a media definition, projects the
share through its selection profile, swaps the provider, assembles the WinPE
media tree and burns one bootable ISO.

The correctness heart is `Get-HDTMediaProjection` and it is PURE: given a
workspace shape and a profile id, which artifacts are projected and which are
refused. It is written and proved first, against hand-written fakes, with no ISO,
no ADK and no disk. Everything after it is assembly.

Purpose: on 2026-09-03 a Generation 2 VM with no network adapter deployed
Windows 11 from a hand-built ISO and finished PNP-TEST, all 15 steps. The ENGINE
side of media works and is not this phase's problem. What built that disc was a
scratchpad script doing by hand what DESIGN 6.2 says a command does. This is the
command.

Output: `Update-HDTMediaContent`, the projection behind it, and the four
refusals a real disc taught us — each of which cost a rebuild.
</objective>

<design_decisions>
Five calls this plan makes. They are made from the evidence above; none needs
confirming, and each is stated here so the tasks can be short.

**1. The projection is a LIST OF ROWS, not a copy.** `Get-HDTMediaProjection`
returns one row per thing that travels and one per thing refused. It copies
nothing and creates nothing. That is what makes projection completeness — the
correctness heart — provable in milliseconds against a fake, and it is DESIGN
12.2.1's rule that a ceremony is asserted by its exact ordered operation list.

Each row: `Kind` (`Marker`, `Document`, `Control`, `Content`, `Excluded`),
`Source` (share-relative), `Destination` (relative to `\Share`), `Reason` (a
sentence), `Present` (`[bool]`), `Rewritten` (`[bool]`).

**2. What travels, in this order, and the order is the log's order:**

| # | Source | Why |
|---|---|---|
| 1 | `rules.yaml` | **the content marker.** `Resolve-HDTDeployRoot` hunts every ready volume for it; a disc without it is invisible. No profile may omit it |
| 2 | `workspace.yaml` | travels **rewritten** — see decision 3 |
| 3 | `Control\` | selection-profiles.yaml and the per-machine rules under `Control\machines`; a media deployment resolves rules exactly as a share deployment does. **Minus `share-credential.json`** |
| 4… | each `Expand-HDTSelectionProfile` row | `Applications\`, `OperatingSystems\`, `Drivers\`, `TaskSequences\`, `Scripts\` — whatever the profile names |

**3. The provider swap is one key and the credential block goes.** The projected
`workspace.yaml` gets `deployRoot: \Share` — the volume-relative form, NOT
expanded to a letter, because the letter the disc lands on is the one value that
is certainly wrong — and its `credential:` block is removed. Both edits are
splices through `Set-HDTWorkspaceKey`, which already builds and removes blocks:
`-Path 'deployRoot' -Text '\Share'` and `-Path 'credential' -Text @()`. **Its own
header says removing a key that was the last thing in its block removes the
block**, which is exactly what is wanted. No re-serialisation, so the comments an
administrator wrote survive onto the disc.

**4. The boot image is built FROM THE PROJECTED SHARE, with `-SkipIso`.** This is
the decision worth being explicit about, because the alternative looks cheaper
and is wrong.

Copying the share's existing `Boot\HDTPE_x64.wim` onto the disc would put an
**Smb** image on it whenever the share's `deployRoot` is a UNC path — which is
every real share. The image derives its provider from the `workspace.yaml` it was
built against, so the only honest way to get a Local image is to build against
the projected one:

```
Update-HDTBootImage -WorkspaceRoot <staging>\media\Share -SkipIso -Progress $Progress
```

It writes `<staging>\media\Share\Boot\HDTPE_x64.wim`. Move that to
`<staging>\media\sources\boot.wim`, then **remove `<staging>\media\Share\Boot`** —
a directory this process created in this run, which is a permitted delete
(PROJECT.md), and the fourth refusal above. `-SkipIso` because
`Update-HDTBootImage` would otherwise burn a debugging ISO nobody asked for, in
the middle of building the one that was.

**5. The dependency finding WARNS and does not fix.** `Resolve-HDTApplicationOrder`
already computes the transitive closure. Run it over the applications the
projection carries; anything in the resulting plan that the projection does NOT
carry is a missing dependency, and it is reported naming **both** applications —
the one that is on the disc and the one it needs. **Do not add it.** DESIGN 6.2:
the profile is the administrator's statement of intent, and MDT would have let
the machine find out on the bench. HDT says so hours earlier, in front of the
person who can fix it.
</design_decisions>
