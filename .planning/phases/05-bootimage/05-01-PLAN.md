### `Get-HDTAdkPath`

```
Get-HDTAdkPath -Asset <string> [-Architecture <amd64|arm64>] [-Root <string>]
               [-Registry <object>] [-FileSystem <object>] [-Language <string>]
               [-SkipExistenceCheck]
Get-HDTAdkPath -All   [-Architecture …] [-Root …] [-Registry …] [-FileSystem …]
```

`-Asset` is a **closed** `ValidateSet` — an unknown asset is a defect, not a
path, exactly as `Get-HDTWorkspacePath -Kind` is closed:

| Asset | Path |
|---|---|
| `Root` | `<KitsRoot10>Assessment and Deployment Kit` |
| `DeploymentTools` | `<root>\Deployment Tools\<arch>` |
| `OscdimgDirectory` | `<root>\Deployment Tools\<arch>\Oscdimg` |
| `Oscdimg` | `…\Oscdimg\oscdimg.exe` |
| `EtfsBoot` | `…\Oscdimg\etfsboot.com` |
| `EfiSys` | `…\Oscdimg\efisys.bin` |
| `EfiSysNoPrompt` | `…\Oscdimg\efisys_noprompt.bin` |
| `WinPeRoot` | `<root>\Windows Preinstallation Environment\<arch>` |
| `WinPeWim` | `<winPeRoot>\<language>\winpe.wim` |
| `WinPeMedia` | `<winPeRoot>\Media` |
| `WinPeOptionalComponent` | `<winPeRoot>\WinPE_OCs` |
| `WinPeOptionalComponentLanguage` | `<winPeRoot>\WinPE_OCs\<language>` |

- `-Language` defaults to `en-us`.
- Root resolution order, and it stops at the first that answers:
  1. `-Root`, when given;
  2. `IRegistryService.GetValue('HKLM:\SOFTWARE\WOW6432Node\Microsoft\Windows Kits\Installed Roots', 'KitsRoot10')`;
  3. `IRegistryService.GetValue('HKLM:\SOFTWARE\Microsoft\Windows Kits\Installed Roots', 'KitsRoot10')`
     — the 32-bit view, for a session that is not WOW-redirected.
  There is **no** fallback to a literal `C:\Program Files (x86)\…`: PROJECT.md
  says resolve at runtime because the layout has moved between ADK releases, and
  a hardcoded fallback is how that rule gets quietly broken. When no key answers,
  throw naming both keys and telling the operator to install the Deployment Tools.
- The returned root has its trailing separator normalised away
  (`KitsRoot10` ends with `\` and `[IO.Path]::Combine` would not care, but the
  manifest records these strings and a doubled separator in a manifest is noise).
- **Every asset is existence-checked through `IFileSystem.TestPath` and a miss
  throws**, naming the asset, the path it looked at, and which ADK feature
  installs it (Deployment Tools vs the WinPE add-on). `-SkipExistenceCheck` turns
  that off, and exists for exactly one caller: the unit test that asserts path
  *construction* independently of what is installed.
- `-All` returns one row per asset — `Name`, `Path`, `Exists` — sorted by the
  table order above, and never throws. That is what the build manifest records
  and what an operator runs when a build fails.
- Errors are `HDTDependencyError`, matching `ConvertFrom-HDTYaml`'s missing-parser
  class, because a missing ADK is the same kind of problem.

### `workspace.yaml`

```yaml
schemaVersion: 1
id: HDT-LAB                       # required, [A-Za-z0-9-_]{1,64}
name: HDT lab deployment share    # required
deployRoot: \\server\HdtShare     # required - what a booted client connects to
logLevel: Info                    # optional: Error|Warning|Info|Debug
credential:
  username: CONTOSO\svc-hdt-deploy
bootImage:
  name: HDTPE_x64                 # artifact base name; default HDTPE_<arch>
  architecture: amd64             # amd64|arm64, default amd64
  language: en-us                 # default en-us
  scratchSpaceMB: 512             # 32..1024, default 512
  optionalComponents:             # merged with the required set, order preserved
    - WinPE-SecureStartup
    - WinPE-EnhancedStorage
    - WinPE-WDS-Tools
  extraContent:
    - source: Modules\MyVendorTools
      destination: \HDT\Modules\MyVendorTools
  drivers: boot-critical          # a group under Drivers\, or absent
```

**`credential:` carries a username and NOTHING ELSE.** DESIGN 6.3 says
"`Set-HDTShareCredential` writes it; the value never appears in a file an admin
hand-edits, so it does not end up in git" — which is incompatible with the
password living in `workspace.yaml`, the file an admin hand-edits. The secret
lives in `Control\share-credential.json`, written only by `Set-HDTShareCredential`
in 05-02. **A `password:` key under `credential:` is a validation error** whose
message names `Set-HDTShareCredential` and says the secret does not belong in
this file. Record the DESIGN 6.3 correction in the summary.

Validation rules, each one a failing test before the code:

| Rule | Error mentions |
|---|---|
| `schemaVersion` missing | the file, `schemaVersion` |
| `schemaVersion` newer than the engine supports | the file, both numbers |
| unknown top-level key | the file, the key, the accepted keys |
| unknown key under `bootImage` | the file, `bootImage`, the key |
| `id` / `name` / `deployRoot` missing | the file, the key |
| `id` with a character outside `[A-Za-z0-9-_]` | the file, the offending value |
| `optionalComponents` not a list | the file, the key |
| a component not matching `^WinPE-[A-Za-z0-9-]+$` | the file, the value |
| a duplicate component (case-insensitive) | the file, the value |
| `extraContent` entry missing `source` or `destination` | the file, the index, the key |
| `extraContent` destination not starting `\` | the file, the value, "a destination is a path inside the image" |
| `extraContent` destination containing `..` | the file, the value, "escapes the image" |
| `credential.password` present | the file, `Set-HDTShareCredential` |
| `scratchSpaceMB` outside 32..1024 | the file, the value |
| `logLevel` outside the four | the file, the value, the four |
| unparseable YAML | the file **and the line** — `ConvertFrom-HDTYaml` already does this |

`Import-HDTWorkspaceDocument -Path <file> -FileSystem <object>` reads through
`IFileSystem`, parses with `ConvertFrom-HDTYaml`, validates, and projects to a
`[pscustomobject]` with **defaults already applied**, so no caller repeats them:

```
SchemaVersion, Id, Name, DeployRoot, LogLevel, Path,
Credential      -> { Username }        ($null when no credential block)
BootImage       -> { Name, Architecture, Language, ScratchSpaceMB,
                     OptionalComponent [string[]], ExtraContent [rows of
                     {Source, Destination}], Drivers }
```

`BootImage` is **never `$null`** — an absent `bootImage:` block yields the
defaults, because "the admin did not say" and "the admin said nothing unusual"
are the same build.

### `Get-HDTBootImageComponent`

```
Get-HDTBootImageComponent [-OptionalComponent <string[]>] -ComponentRoot <string>
                          [-Language <string>] [-FileSystem <object>]
```

Returns one row per component, **in the order they must be applied**:

```
Order   [int]     1-based
Name    [string]  WinPE-WMI
Required[bool]    true for the six
CabPath [string]  <root>\WinPE-WMI.cab
LanguageCabPath   [string]  <root>\en-us\WinPE-WMI_en-us.cab, or '' when none
```

**The required set, in this order, and this is SPIKES S1's verified order — not a
list to re-sort:**

```
WinPE-WMI -> WinPE-NetFx -> WinPE-Scripting -> WinPE-PowerShell
  -> WinPE-StorageWMI -> WinPE-DismCmdlets
```

Note `WinPE-NetFx` — **lowercase x**. DESIGN 5.1 says an earlier draft wrote
`WinPE-NetFX` and it did not exist. Put a test on that spelling by name.

The defaults DESIGN 5.1 adds on top, applied when the caller supplies **no**
`-OptionalComponent` at all: `WinPE-SecureStartup`, `WinPE-EnhancedStorage`,
`WinPE-WDS-Tools`. An **explicit empty array** means "the six and nothing else"
and is honoured — that is the difference between unset and set-to-nothing, and
it gets its own test.

Merge rules:
- the six always come first, in their order, whatever the caller said;
- a caller's component that is already required is dropped from the tail rather
  than applied twice, and its position does not reorder the six;
- the caller's remaining components keep the order the caller wrote (DESIGN 5.1:
  "merged with the required set below, order preserved");
- comparison is case-insensitive throughout.

Dependency validation, from the private table
`Get-HDTBootImageComponentDependency` (Microsoft's documented WinPE OC
dependencies, restricted to what this repo can name honestly):

```
WinPE-NetFx          -> (none)
WinPE-Scripting      -> (none)
WinPE-PowerShell     -> WinPE-WMI, WinPE-NetFx, WinPE-Scripting
WinPE-StorageWMI     -> WinPE-WMI, WinPE-NetFx, WinPE-Scripting, WinPE-PowerShell
WinPE-DismCmdlets    -> WinPE-WMI, WinPE-NetFx, WinPE-Scripting, WinPE-PowerShell
WinPE-SecureStartup  -> WinPE-WMI
WinPE-WDS-Tools      -> WinPE-WMI
WinPE-EnhancedStorage-> (none)
WinPE-Dot3Svc        -> WinPE-WMI, WinPE-NetFx, WinPE-Scripting, WinPE-PowerShell
WinPE-WiFi-Package   -> WinPE-WMI, WinPE-NetFx, WinPE-Scripting, WinPE-PowerShell
```

A component **not in the table** is allowed with no dependencies and no warning —
the whole point of DESIGN 5.1 is that a fleet needs components this project never
anticipated. A component **in** the table whose dependency is absent from the
final list is **refused**, naming both, and telling the admin to add the
dependency to `optionalComponents`. HDT does not silently insert it: an admin who
is told gets a boot image they understand.

Filesystem contact, and only this:
- `CabPath` must exist → otherwise throw, naming the component, the path, and
  `<ComponentRoot>`. A build that applies a cab that is not there fails fifteen
  minutes in, having mounted a WIM.
- `LanguageCabPath` is **probed**. Absent → the property is `''` and a
  `Write-Warning` says so once, naming the component. This is `WinPE-FMAPI`'s row
  and it must never be an error.
