**The interface.** Six methods. Decide nothing else; this is the contract.

| Method | Signature | Returns |
|---|---|---|
| `SetServer` | `([string] $Url)` | nothing |
| `SearchUpdate` | `([string] $Criteria)` | `object[]`, one row per update |
| `AcceptEula` | `([string] $UpdateId)` | nothing |
| `DownloadUpdate` | `([string[]] $UpdateId)` | a result object |
| `InstallUpdate` | `([string[]] $UpdateId)` | a result object |
| `GetRebootRequired` | `()` | `[bool]` |

An update row carries: `UpdateId [string]`, `Title [string]`,
`KBArticleId [string[]]`, `Category [string[]]`, `IsDownloaded [bool]`,
`EulaAccepted [bool]`, `SizeByte [long]`.

A `DownloadUpdate` / `InstallUpdate` result carries: `Success [bool]`,
`ResultCode [int]`, `HResult [int]`, `RebootRequired [bool]`, and
`PerUpdate [object[]]` with `UpdateId`, `ResultCode`, `HResult` per element.

Two design decisions to write into the contract file's header comment, because
both will be questioned:

- **`SearchUpdate` is flat and unfiltered.** It returns every update the search
  criteria matched, with its categories and its KB numbers, and it filters
  nothing. Deciding which of those to install — the category list, the exclude
  patterns, the explicit KB numbers — is pure logic that can be tested, and it
  belongs in the step. This is `IDiskService`'s three flat listings and
  `IFeatureService.GetFeature()`'s reason, again.
- **`SetServer` IS on the adapter and not in the step**, even though pointing a
  client at WSUS is four registry values and a service restart. PSD's
  `PSDWindowsUpdate.ps1` writes `WUServer`, `WUStatusServer`,
  `AU\UseWUServer = 1`, `AU\NoAutoUpdate = 1` under
  `HKLM\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate` and then restarts
  `wuauserv`, and none of that is a decision — it is the IO that makes a
  `ServerSelection` of `ssManagedServer` mean anything. **The step decides
  whether to call it; the adapter does it.** That keeps the adapter branch-free:
  it is only ever called with a URL, so it never has to ask whether it has one.

Parameters the fake needs, so the step's tests can drive every branch:

- `-Update [object[]]` — the rows `SearchUpdate` returns. Default: a small set
  that exercises categories and KB numbers.
- `-InstallResult [hashtable]` — update id to `@{ ResultCode; HResult;
  RebootRequired }`. Default: everything succeeds, nothing reboots.
- `-DownloadResult [hashtable]` — the same, for downloads.
- `-RebootRequired [bool]` — what `GetRebootRequired` answers.
- `-UpdatePerPass [object[][]]` — **the one the multi-pass loop needs.** An array
  of arrays: pass 1 returns the first element, pass 2 the second, and so on, with
  the last element repeating once the array is exhausted. This is how a test says
  "installing this update revealed another one", which is the entire point of
  DESIGN 10.1's loop and cannot be expressed with a single fixed result.
- `-FailSearch [switch]`, `-FailInstall [switch]` — the agent throwing.

**Important, and this is the trap `tests/helpers/README.md` records for the
filesystem fake:** the fake must behave the way the real thing does or the fake is
wrong, not the caller. Specifically — after a successful `InstallUpdate`, the same
update must NOT come back from the next `SearchUpdate` on the same instance
(unless `-UpdatePerPass` says otherwise), because the real criteria is
`IsInstalled = 0`. A fake that keeps returning an installed update turns the
step's termination test into a test of `maxPasses` and hides an infinite loop.

**Then `New-HDTUpdateSessionService`.** Structure copied from

**IT MUST BE BRANCH-FREE.** No `if`, no `switch`, no `-and`/`-or` used as control
flow, no `try`/`catch` that changes the answer. That is rule 1's only exception
and it is what buys the adapter out of unit testing. A `foreach` that projects a
COM collection into a `[pscustomobject]` is fine; a `foreach` that decides is not.
Every decision — which updates match the categories, which are excluded, whether
to run another pass, whether to reboot — belongs to the step in plan 08-01-03.

The mechanism, from PSD's `PSDWindowsUpdate.ps1` (MIT; **add a derivation comment
on the function and an entry in `NOTICE.md`**) and DESIGN 10.1:

```
SetServer($Url)
  New-Item   HKLM:\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate        -Force
  New-ItemProperty ... -Name WUServer        -Value $Url -Type String -Force
  New-ItemProperty ... -Name WUStatusServer  -Value $Url -Type String -Force
  New-Item   HKLM:\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate\AU     -Force
  New-ItemProperty ...\AU -Name UseWUServer  -Value 1 -Type DWord  -Force
  New-ItemProperty ...\AU -Name NoAutoUpdate -Value 1 -Type DWord  -Force
  Restart-Service -Name wuauserv -Force
```

`NoAutoUpdate = 1` is deliberate and belongs in a comment: during a deployment
the sequence drives patching, and the automatic agent starting its own download
in parallel is how a build ends up with two installers fighting over the same
servicing stack.

```
SearchUpdate($Criteria)
  $session  = New-Object -ComObject 'Microsoft.Update.Session'
  $searcher = $session.CreateUpdateSearcher()
  $searcher.ServerSelection = 1            # ssManagedServer - the WSUS the policy names
  $result   = $searcher.Search($Criteria)  # the step passes 'IsInstalled = 0'
  foreach ($u in $result.Updates) { project into the row shape }
```

`ServerSelection = 1` is `ssManagedServer` and it is what makes the registry
values above take effect for THIS search rather than for the next scheduled scan.
Say so in a comment; it is the line PSD needed a version bump to add.

Projection details that are easy to get wrong and must be commented:
- `KBArticleId` is `$u.KBArticleIDs`, a COM string collection — project with
  `[string[]] @(@($u.KBArticleIDs) | ForEach-Object { [string] $_ })`. The numbers
  come back WITHOUT the `KB` prefix; keep them as the agent gives them and let the
  step normalise, so the adapter stays a projection.
- `Category` is `@($u.Categories | ForEach-Object { [string] $_.Name })`.
- `SizeByte` is `$u.MaxDownloadSize`.
- The unary comma on a single-element return — a `ScriptMethod` collapses it.
  `New-HDTFeatureService` has the same comment at line ~110; copy it.

```
AcceptEula($UpdateId)   -> find the update by id in the last search, .AcceptEula()
DownloadUpdate($Id[])   -> Microsoft.Update.UpdateColl, session.CreateUpdateDownloader(), .Download()
InstallUpdate($Id[])    -> Microsoft.Update.UpdateColl, session.CreateUpdateInstaller(), .Install()
GetRebootRequired()     -> (New-Object -ComObject 'Microsoft.Update.SystemInfo').RebootRequired
```

`GetRebootRequired` reads the machine (`ISystemInformation.RebootRequired`), not
the last install result. Both matter and they are different questions: the install
result says "this batch asked for a restart", the machine says "there is a restart
pending from anything at all, including the servicing stack update that went in
first". The step needs both.

Batch download and install take the whole collection, but the step calls them
**one update at a time** so it can time and log each — see plan 08-01-03. The
adapter takes `[string[]]` anyway so a future caller can batch without changing
it.

`Install()` returns an `IInstallationResult` with `ResultCode`, `HResult`,
`RebootRequired` and `GetUpdateResult($i)` per update. Project all of them.
`Success` is `ResultCode -eq 2` (`orcSucceeded`) — and that comparison is a
projection of a documented enum, not a decision, so it stays. Note the codes in a
comment: 0 NotStarted, 1 InProgress, 2 Succeeded, 3 SucceededWithErrors, 4 Failed,
5 Aborted.
