### The condition grammar — closed, and parsed at authoring time

DESIGN 3.3 says HDT deliberately has no condition language, and DESIGN 4.1 uses
exactly one shape: `"%_HDTPhase%" == "OS"`. So the grammar is:

```
<condition> := <operand> <operator> <operand>
<operand>   := '"' anything-but-a-double-quote '"'   |   a token with no whitespace
<operator>  := == | != | -eq | -ne | -like | -notlike
```

- `ConvertFrom-HDTStepCondition -Condition <string>` returns
  `[pscustomobject] @{ Left; Operator; Right; Text }` or throws
  `HDTConfigurationError` naming the condition. It is called by
  `Assert-HDTSequenceDocument`, so a malformed condition fails at **import**, not
  mid-deployment.
- `Test-HDTStepCondition -Condition <string> -Variable <IDictionary> [-Unresolved]`
  expands `%Var%` on both operands with `Expand-HDTVariableToken`, renders both
  through `ConvertTo-HDTComparableString`, and compares case-insensitively.
  `-like`/`-notlike` use wildcards; the rest are equality.
- An absent, empty or whitespace-only condition is `$true`.
- An unresolved `%Var%` leaves the token literal (02-03's rule), so the
  comparison simply fails; the token name is reported through `-Unresolved` and
  the loop logs it. **Not** an error — a condition that silently becomes `""` is
  how MDT-era task sequences ran the wrong branch.

**DESIGN 4.1 has two bugs in one line and this plan fixes both in code and
reports both:**

1. **The value is wrong.** It reads `== "OS"`, but DESIGN 4.4.1 defines
   `_HDTPhase` as `WinPE` or `FullOS`, so `"OS"` never matched anything.
2. **The line is not valid YAML.** `condition: "%_HDTPhase%" == "OS"` opens a
   double-quoted scalar, closes it after `%_HDTPhase%`, and then carries trailing
   content on the same line — every YAML parser rejects it. Because a condition
   carries double quotes as part of its own grammar, **the whole condition must
   be a single-quoted YAML scalar**:

   ```yaml
   condition: '"%_HDTPhase%" == "FullOS"'
   ```

   Every condition in every fixture, sample and doc example this phase writes
   uses that form. `invalid-bad-condition.yaml` is the exception that proves it:
   `condition: "%A% =~ 1"` puts the whole condition inside one pair of double
   quotes, so it is **valid YAML carrying an invalid condition** — which is what
   makes it test the condition grammar rather than the parser, the job
   `unparseable-indentation.yaml` already has. Getting that distinction wrong
   would leave `ConvertFrom-HDTStepCondition`'s error path untested.

03-05's docs task corrects DESIGN 4.1 for **both**, not just the value.

### The sequence document

```
Import-HDTSequenceDocument -Path <string> -FileSystem <object> -> [pscustomobject]

  Path, SchemaVersion, Id, Name, Description
  Variable  ordered, case-insensitive: the sequence defaults (DESIGN 3.1 source 5)
  Step      [object[]] FLATTENED into execution order
  Group     [object[]] one per group node: Path (string[]), Condition, RunIn
```

A flattened step record:

| Property | Meaning | Default |
|---|---|---|
| `Index` | 1-based position in execution order | — |
| `Name` / `Type` | from the document | — |
| `GroupPath` | `[string[]]`, outermost first, `@()` at the root | `@()` |
| `Condition` | the step's own condition | `$null` |
| `GroupCondition` | `[object[]]` of `@{ Group; Condition }`, outermost first, only for ancestors that declare one | `@()` |
| `ContinueOnError` | bool | `$false` |
| `TimeoutMinutes` | int, `0` = unbounded | `0` |
| `RunIn` | `WinPE` \| `FullOS` \| `Any`; a step with none inherits its nearest ancestor group's `runIn` | `Any` |
| `Retry` | `@{ Count = 0; DelaySecond = 0; Backoff = 'fixed' }` | as shown |
| `Resumable` | bool — DESIGN 4.3's "re-runs the interrupted one only if the step declares `resumable: true`" | `$false` |
| `Log` | a per-step log file name (DESIGN 4.4.4) | `$null` |
| `Property` | ordered dictionary of every key that is **not** a common property — the step type's own arguments | — |

**Flattening is the design decision of this task.** A group is not an execution
unit; it is a naming and condition device. Flattening to a linear list means
resume by index works unchanged with nesting, and a group whose condition is
false produces one `step.skip` record per contained step naming the group — which
is what a technician reading the log needs, rather than a single line that hides
six steps.

Validation (`Assert-HDTSequenceDocument`, the WinPE-side validator, mirroring
`Assert-HDTRuleDocument`'s shape exactly):

- document: a mapping; only `schemaVersion`, `id`, `name`, `description`,
  `variables`, `steps`; `schemaVersion` through `Test-HDTSchemaVersion`; `id`
  matching `^[A-Za-z0-9][A-Za-z0-9_-]*$`; `name` non-empty; `steps` a non-empty list.
- node: a mapping; a **group** node has `group` and `steps` and no key outside
  `group`/`condition`/`runIn`/`steps`; a **step** node has `name` and `type`; a
  node with both `group` and `type` is an error naming it (this is the one case
  `oneOf` in JSON Schema cannot reject, so it is the documented schema blind spot).
- step: `name` non-empty; `type` matching `^[A-Za-z][A-Za-z0-9]*$`;
  `continueOnError`/`resumable` boolean; `timeoutMinutes` a positive integer;
  `runIn` in the set; `retry` a mapping with `count` 0-10, `delaySeconds` >= 0,
  `backoff` in `fixed`/`exponential`; `condition` parseable.
- variables: every name matching `^HDT[A-Za-z0-9_]*$`, no `_HDT*` (DESIGN 3.2).
- **Step types are NOT validated here.** Types are pluggable and discovered at
  runtime; a sequence authored for a workspace whose `Modules\` carries a
  third-party step must still import on a machine that does not. An unknown type
  fails the *step*, at execution, naming the known types.

### Discovery by convention

A step type `<Type>` is implemented by:

| Function | Required | Default when absent |
|---|---|---|
| `Invoke-HDT<Type>Step -Step -Context` | yes | — |
| `Test-HDT<Type>StepApplicable -Step -Context` | no | `$true` |
| `Get-HDT<Type>StepDescription -Step` | no | `'<Type>: <name>'` |

```
Get-HDTStepType [-Name <string[]>] -> [pscustomobject] @{ Type; InvokeCommand; TestCommand; DescriptionCommand; Source }
```

It enumerates `Get-Command -CommandType Function -Name 'Invoke-HDT*Step'` in the
session and keeps what matches `^Invoke-HDT(?<type>[A-Za-z0-9]+)Step$`, so a
module imported out of `Modules\` contributes without the engine knowing it
exists. Two modules exporting the same type is a terminating error naming both
sources — a third party silently shadowing `ApplyImage` is exactly the failure
that must not be quiet. **No future HDT function may be named
`Invoke-HDT*Step`** unless it is a step type; note it in the summary.

`Import-HDTStepModule -Path <string>` is a thin, branch-free adapter over
`Import-Module` for the workspace's `Modules\` directory. It is not unit tested
beyond "it calls Import-Module for each .psd1/.psm1 it is given"; the discovery
tests use `New-Module | Import-Module` instead.

### The step contract

Every step is called as `Invoke-HDT<Type>Step -Step $step -Context $context` and
returns `New-HDTStepResult`:

```
[pscustomobject] @{ Status; ExitCode; Message; Data }
    Status  Completed | Failed | RebootRequested
```

`$Context` is the execution context:

```
New-HDTExecutionContext -RunId -Phase -WorkspaceRoot -Variable -Service -Log [-State]

  RunId, Phase, WorkspaceRoot
  Variable   ordered case-insensitive dictionary, LIVE - a step may write to it
  Service    the service catalog
  Log        the 03-01 log context
  State      the 03-01 run state, or $null
  Attempt    the 1-based attempt number, set by the loop before each call
  SetStep($index, $name, $type)   updates _HDTStepName/_HDTStepType and the log context
```

It seeds the engine variables DESIGN 4.4.1 defines: `_HDTRunId`, `_HDTPhase`,
`_HDTLogPath`, `_HDTDeployRoot`, `_HDTVersion`, and per step `_HDTStepName` and
`_HDTStepType`. They are readable by conditions and by user scripts and are never
assignable from a sequence (`Assert-HDTSequenceDocument` already refuses).

```
New-HDTServiceCatalog -FileSystem -Clock [-Registry] [-Lsa] [-Process] [-Power]
                      [-ScriptInvoker] [-Cim] [-Environment]

  every property is defined, $null where not supplied
  GetRequired('Process')  -> the service, or a terminating error naming the
                             service and the step type that asked for it
```

`FileSystem` and `Clock` are mandatory; everything else is optional, because a
`NoOp` sequence must be runnable with two services and no more.

### The five steps

| Type | Properties | Behaviour |
|---|---|---|
| `NoOp` | `message`, `fail` (bool), `failAttempt` (int), `exitCode`, `requestReboot` (bool) | Logs and returns. `failAttempt: 2` fails attempts 1 and 2 and succeeds on 3 — this is how 03-04 proves retry without a real flaky thing |
| `SetVariable` | `variables` (mapping) or `variable` + `value` | Expands `%Var%` against the live dictionary, writes into `$Context.Variable`, logs one `var.resolve` per name with `data.source = 'Step'`. Refuses `_HDT*` |
| `PowerShell` | `script` (required, relative to the workspace root), `log` | `$Context.Service.ScriptInvoker.Invoke($script, $Context.Variable)`; the transcript is written into the per-step log; a thrown exception is `Failed` with its message |
| `CommandLine` | `command`, or `file` + `arguments`; `workingDirectory`, `successCodes` (default `[0]`), `rebootCodes` (default `[3010]`) | Through `IProcessService`. `command` runs via `%ComSpec% /c` so it behaves like MDT's Run Command Line; `file`+`arguments` starts directly. Exit code in `successCodes` → `Completed`, in `rebootCodes` → `RebootRequested`, otherwise `Failed` naming the code |
| `Restart` | `delaySeconds`, `message` | Returns `RebootRequested`. **It does not arm autologon and does not call the power service** |

**Why `Restart` does not reboot:** the reboot ceremony is arm autologon → save
state → log `reboot.arm` → restart, and a failure between any two of those must
leave a machine that can still be recovered. That ordering belongs to the loop
(03-04), which owns the state document. A step that rebooted itself could not be
checkpointed, which is the bug this design exists to avoid.

### `SetVariable` and provenance

02-03 closed the provenance `Source` set deliberately. A `SetVariable` step is
**not** a sixth source in that set: it is an imperative mid-sequence assignment
that *must* be able to overwrite, whereas `Add-HDTResolvedVariable` refuses to.
So `SetVariable` writes `$Context.Variable` directly and its provenance is the
`var.resolve` record on the JSONL stream carrying `data.source = 'Step'` and the
step name. `Add-HDTResolvedVariable`'s `ValidateSet` is not touched.

### IProcessService and IPowerService

```
Start([string] $FilePath, [string] $Argument, [string] $WorkingDirectory, [int] $TimeoutMillisecond)
  -> [pscustomobject] @{ ExitCode; StandardOutput; StandardError; TimedOut; DurationMs }
     TimeoutMillisecond 0 = unbounded; on timeout the process is killed,
     TimedOut is $true and ExitCode is -1

Restart([int] $DelaySecond)
Stop([int] $DelaySecond)
```

The real `New-HDTProcessService` is a `ProcessStartInfo` + `WaitForExit(timeout)`
adapter. The real `New-HDTPowerService` shells `shutdown.exe /r /t <delay> /f`
with a `-Command` parameter to override it. **Record as unverified for phase 05:**
whether `shutdown.exe` is the right call inside WinPE, or whether it must be
`wpeutil reboot`. Nothing in this phase reboots anything, so the question is
deferred honestly rather than guessed at.

The fake process service is seeded by command line:

```
New-HDTFakeProcessService -Result @{ 'cmd.exe /c exit 3010' = @{ ExitCode = 3010 } }
```

An unseeded command throws `System.ComponentModel.Win32Exception`, which is what
`Process.Start` throws for a missing executable — the parity rule in
tests/helpers/README.md section 5.

### IScriptInvoker gains a transcript

DESIGN 4.4.4 requires that a user script writing only to `Write-Host` still lands
in the log. So `IScriptInvoker` gains one method:

```
GetTranscript() -> [string[]]   the captured output of the LAST Invoke
```

The real adapter changes from `& $script -Variable $v | Select-Object -Last 1` to
capturing `*>&1`, storing every item rendered as text in the transcript, and
returning the last item that is **not** a stream record
(`InformationRecord`, `ErrorRecord`, `WarningRecord`, `VerboseRecord`,
`DebugRecord`). That is a branch inside an adapter, which the "adapters stay
dumb" rule tolerates only because the contract test proves it on both
implementations — write that test.

`HDTFakeScriptInvoker` gains the matching half, and **the parameter name is fixed
here because 03-05's headline-test harness is already written against it**:

```
New-HDTFakeScriptInvoker [-Result <hashtable>] [-Transcript <hashtable>] [-Journal]

  SeedTranscript([string] $Path, [string[]] $Line)   seeding, never recorded
  GetTranscript() -> [string[]]                      the transcript of the LAST
                                                     Invoke; @() when the path
                                                     was seeded without one, and
                                                     @() before any Invoke
```

Transcript seed keys are normalised exactly as `-Result` keys already are — case
insensitive, `\` folded to `/` — so one key serves both hashtables. The unary
comma rule (README F3) does not apply to the fake, which is a class, but it
**does** apply to `New-HDTScriptInvoker`'s `GetTranscript`, which is a
`ScriptMethod` and would otherwise collapse a one-line transcript to a string.
