- **`ConvertTo-Json` serialises a `[datetime]` differently on the two engines.**
  Probed: pwsh 7.5.8 emits `"2026-08-13T00:11:02.481Z"`, Windows PowerShell

<engine_semantics>
**Read this section before writing any test. It is the specification the tests
encode; everything in it is a decision, not a suggestion.**

### The scope

`Resolve-HDTVariable` keeps one dictionary, `$scope`, holding **raw
(unexpanded)** values. It is built once, then updated on every assignment:

1. seed with `-SequenceDefault`
2. overwrite with `-Fact`
3. thereafter, every assignment writes its **raw** value into `$scope`

Lookup precedence therefore falls out of write order: an assigned value shadows a
fact, a fact shadows a sequence default. `$scope` is what `when` matching and
`%Var%` expansion read. The **expanded** value is what lands in the result.

Keeping raw values in `$scope` is what makes cycle detection meaningful: two
variables whose raw values reference each other are a cycle, and eager expansion
alone would hide it.

### Resolution order

| Step | Source | Provenance `Source` |
|---|---|---|
| 1 | `-CommandLine` | `CommandLine` |
| 2 | `-MachineOverride` | `MachineOverride` |
| 3 | `-RuleDocument`, rules walked top to bottom | `Rule`, or `RuleScript` for `setFrom` |
| 4 | `-Fact` | `GatheredFact` |
| 5 | `-SequenceDefault` | `SequenceDefault` |

Every write goes through `Add-HDTResolvedVariable`, which refuses to overwrite an
already-resolved variable. First writer wins, so applying the sources in this
order *is* DESIGN 3.1's precedence, and a later fallback rule can only fill what
nothing above it set.

Within a rule, `set` keys are applied in **document order** (which is why 02-02
normalises to an ordered dictionary), and the scope updates as each is applied —
so a later key in the same rule may expand a `%Var%` set by an earlier one, and a
later rule may match on a value an earlier rule set.

### `when` matching (`Test-HDTRuleMatch`)

- No `when`, or an empty `when` → matches. That is DESIGN 3.3's `Fallback` rule.
- All keys must match (AND).
- The pattern is `%Var%`-expanded before comparison.
- The key must exist in `$scope` and its value must not be `$null`; otherwise no
  match. An absent fact never matches, including against an empty pattern.
- A list-valued scope entry matches if **any** element matches — `HDTDefaultGateway`
  is a list on a multi-NIC machine, and MDT's `DefaultGateway` behaves the same.
- Operator selection: if the expanded pattern contains `*` or `?` use `-like`,
  otherwise `-eq`. Both are case-insensitive. Choosing per pattern keeps a model
  name containing `[` from being read as a character class.
- Comparison is on strings produced by `ConvertTo-HDTComparableString`, so
  `HDTIsLaptop: true` in YAML matches the `[bool] $true` fact.

### `%Var%` expansion (`Expand-HDTVariableToken`)

- Token grammar: `%Name%` where `Name` matches `[A-Za-z_][A-Za-z0-9_]*`.
- `%%` is a literal `%`.
- A token naming a variable in `$scope` is replaced by that variable's raw value,
  **recursively expanded**, with the token name pushed onto a chain.
- A token already on the chain is a **cycle**: throw a configuration error whose
  message shows the chain, e.g.
  `the value of HDTA cannot be expanded: %HDTA% -> %HDTB% -> %HDTA% is cyclic`.
  Never loop, never guard with a depth counter alone.
- A token naming nothing in `$scope`, or naming a `$null`, is left **literally**
  in the output and its name is recorded in the result's `Unresolved` list. It is
  not an error: MDT leaves such a token alone, and silently emptying it hides
  authoring mistakes. `Unresolved` is what makes it visible.
- A list value referenced inside a string joins with `,`.
- Only `[string]` values are expanded. Booleans, numbers and other types pass
  through untouched; an array is expanded element by element by the caller.

### Provenance record

One `[pscustomobject]` per resolved variable:

| Property | Meaning |
|---|---|
| `Name` | the variable |
| `Value` | the expanded value that was stored |
| `Source` | one of `CommandLine`, `MachineOverride`, `Rule`, `RuleScript`, `GatheredFact`, `SequenceDefault` — a closed set |
| `Rule` | the rule name, or `$null` |
| `RuleIndex` | the 1-based rule index, or `0` |
| `File` | `rules.yaml`, the machine override file, or the `setFrom` script — `$null` for command line, facts and defaults |
| `RawValue` | the value before expansion |
| `Expanded` | `$true` when `Value` differs from `RawValue` |
| `Order` | 1-based order of resolution |

### `Resolve-HDTVariable` result

```
[pscustomobject] @{
    Variable   = <ordered, case-insensitive>  name -> expanded value
    Provenance = <ordered, case-insensitive>  name -> provenance record
    Unresolved = [string[]]                   distinct unresolved token names, sorted ordinal
}
```

### `setFrom`

- Requires `-ScriptInvoker`. A `setFrom` rule that matches with no invoker
  supplied is a configuration error naming the rule.
- The invoker is called as `Invoke($rule.SetFrom, $scopeCopy)` — a **copy** of
  the scope, so a user script cannot mutate engine state.
- The returned object's properties become variables: `[pscustomobject]` via
  `PSObject.Properties`, `IDictionary` via its keys. Both are supported.
- `$null` return sets nothing and is not an error.
- A property named `_HDT*` is a configuration error naming the rule and the
  script (DESIGN 3.2).
- A script that throws is wrapped in a configuration error naming the rule and
  the script, with the original exception kept as the inner exception.
</engine_semantics>

### 3b. `Get-HDTVariableProvenance` and `Export-HDTVariableProvenance`

```
Get-HDTVariableProvenance -Resolution <object> [-Name <string[]>]
    -> provenance records, ordered by Order; -Name filters, wildcards supported

Export-HDTVariableProvenance -Resolution <object> -Path <string> -FileSystem <object>
                             [-Timestamp <datetime>]
    -> writes DESIGN 4.4's Gather\provenance.json through IFileSystem
```

The JSON document:
```json
{ "schemaVersion": 1,
  "generated": "2026-08-13T00:11:02.4810000Z",
  "variable": [ { "name": "...", "value": "...", "source": "Rule", "rule": "Lab subnet",
                  "ruleIndex": 1, "file": "...", "rawValue": "...", "expanded": false, "order": 3 } ] }
```
`-Timestamp` defaults to `[datetime]::UtcNow` and exists so a test can assert on
an exact document. **Format it to a string before serialising** —
`$Timestamp.ToUniversalTime().ToString('o', [System.Globalization.CultureInfo]::InvariantCulture)`
— because `ConvertTo-Json` renders a raw `[datetime]` as `\/Date(...)\/` under
Windows PowerShell 5.1 and as ISO 8601 under pwsh 7, and 5.1 is the engine in
WinPE. Write with `ConvertTo-Json -Depth 6` through
`$FileSystem.WriteAllText(...)` — never `Set-Content`.

`Describe 'Get-HDTVariableProvenance'`
- `It 'returns every record when no name is given'`
- `It 'returns records ordered by Order'`
- `It 'filters by name'`
- `It 'filters by wildcard'`
- `It 'returns nothing for a variable that was never resolved'`
- `It 'returns nothing rather than throwing for an unknown name'`
- `It 'has comment-based help with a synopsis'`

`Describe 'Export-HDTVariableProvenance'`
- `It 'writes the file through the injected filesystem'` — `WriteAllText` appears
  in `GetOperationName()`
- `It 'writes valid JSON'`
- `It 'writes one entry per resolved variable'`
- `It 'writes the entries in resolution order'`
- `It 'writes the timestamp it was given'` — assert the literal string
  `'2026-08-13T00:11:02.4810000Z'`, so the test fails on either engine if the
  `[datetime]` reaches `ConvertTo-Json` unformatted
- `It 'writes the same JSON under both engines'` — assert the `generated`
  value matches `^\d{4}-\d{2}-\d{2}T` and contains no `/Date(`
