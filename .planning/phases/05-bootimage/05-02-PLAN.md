### `IContentProvider` — five members, and both implementations expose all five

```
ResolveContent([string] $RelativePath) -> [string]   an absolute path a step can use
TestContent([string] $RelativePath)    -> [bool]
CopyContent([string] $RelativePath, [string] $Destination) -> [string] the destination
Connect()      -> [string]   the root that is now reachable
Disconnect()   -> void
```

plus the properties every service in this repo carries: `Root`, `ServiceName`
(`ContentProvider`), `Operations`, `Journal`, and `GetOperationName()`.

**`Connect` and `Disconnect` exist on `Local` too, and they are no-ops that still
record.** That is what makes the contract identical from a step's perspective —
DESIGN 6.2's claim. A provider interface where one implementation has two extra
methods is a provider interface a step has to branch on.

Resolution rules, identical in both:
- a **relative** path is combined with `Root`;
- a **rooted** path (`X:\…`, `\\server\…`) is returned unchanged — DESIGN 9.3's
  "media too large to bring into the share is registered where it stands", which
  `ConvertTo-HDTOperatingSystemCatalog` already honours;
- `..` that escapes `Root` is **refused** with `HDTConfigurationError`, naming the
  path and the root. A step asking for content outside the workspace is a defect;
- an empty or whitespace path is refused.

`ResolveContent` does **not** check existence — `TestContent` is the question and
a step asks it when it wants the answer. `CopyContent` throws when the source is
absent.

### `New-HDTLocalContentProvider -Root <path> [-FileSystem] [-Journal]`

Everything through `IFileSystem`. `Connect()` verifies `Root` exists and throws
naming it when it does not — a USB stick that was never inserted must fail here,

### `New-HDTSmbService` — the dumb adapter (untested, branch-free)

```
NewMapping([string] $RemotePath, [string] $UserName, [string] $Password) -> void
RemoveMapping([string] $RemotePath)                                      -> void
GetConnection([string] $ServerName) -> [object[]]   rows of
                                                    { ServerName, ShareName,
                                                      UserName, Dialect,
                                                      Encrypted, Signed }
GetClientConfiguration() -> { EnableInsecureGuestLogons, RequireSecuritySignature }
```

over `New-SmbMapping -RemotePath -UserName -Password -Persistent:$false`,
`Remove-SmbMapping -Force`, `Get-SmbConnection`, `Get-SmbClientConfiguration`.
`SmbShare` is in WinPE, which is why this is the mechanism and not `net use`.
DESIGN 12.2.3: argument construction and nothing else. Its contract row is
`GetClientConfiguration` and `GetConnection` only — read-only, safe on the
developer's machine.

### `New-HDTSmbContentProvider -Root <unc> [-Credential] [-SmbService] [-FileSystem] [-Journal]`

**This is where the decisions live, and they are all unit-testable against
`New-HDTFakeSmbService`.** `Connect()`:

1. Refuse a `Root` that is not UNC → `HDTConfigurationError` naming it.
2. Refuse a `-Credential` with a username and an **empty** password →
   `HDTSecurityError`, message: an empty password is an anonymous logon.
3. Refuse **no credential at all** unless `-AllowAnonymous` was passed
   explicitly. DESIGN 6.3's refusal to fall back to guest starts here: not
   supplying a credential is exactly the fallback.
4. Call `NewMapping`.
5. Read `GetConnection(<server>)` back and **assert the established identity**:
   - no row for the server → throw, the mapping did not take;
   - `UserName` empty, `Guest`, `ANONYMOUS LOGON`, or ending `\Guest`
     (case-insensitive) → **throw `HDTSecurityError`**, naming the server and
     saying the connection fell back to guest and HDT will not deploy from it;
   - `Dialect` starting `1.` → **throw**; SMB1 is refused outright;
   - `Dialect` below `3.0` → **warn** and continue, naming the dialect. A 2.1
     file server is legitimate and refusing it would be HDT deciding a fleet's
     infrastructure for it;
   - `Encrypted` false → **warn** once, naming the server, per DESIGN 6.3's
     "SMB signing and encryption are used where the server supports them".
6. Also refuse before mapping when
   `GetClientConfiguration().EnableInsecureGuestLogons` is `$true` **and** no
   credential was supplied. HDT does **not** change the machine's SMB client
   configuration — it reports it. Changing a machine's security posture to make
   a deployment work is the opposite of what this check is for.

`Disconnect()` calls `RemoveMapping` and never throws — it runs in a `finally`.
Re-entrancy: `Connect()` twice maps once and records once.

### The credential

```
Set-HDTShareCredential -WorkspaceRoot <string> -Credential <pscredential>
                       [-FileSystem] -WhatIf -Confirm
Get-HDTShareCredential -WorkspaceRoot <string> [-FileSystem]  -> { UserName, Password }
```

- Written to **`<workspace>\Control\share-credential.json`** — built with
  `Get-HDTWorkspacePath -Kind Control -ChildPath 'share-credential.json'`, never
  a literal. 05-01 established that `workspace.yaml` refuses a `password:` key;
  this is where the secret actually lives.
- The stored value is **not plain text and is not claimed to be secure**. Use
  AES with a key that is a constant in the module, base64 the result, and write
  a `warning` field into the file itself whose text says, in one sentence, that
  anyone who can read this file or the boot image can recover the password.
  DESIGN 6.3: "obfuscation is not claimed as security … the docs say so plainly
  rather than implying the image is safe to hand out." **Do not use DPAPI** — it
  is user- and machine-bound and the boot image must be readable inside WinPE on
  another machine, which is the whole point.
- `.gitignore` gains `Control/share-credential.json` and
  `**/Control/share-credential.json`.
- `Set-HDTShareCredential` carries `SupportsShouldProcess`: it overwrites a
  secret.

### `Test-HDTShareAcl` and `Get-HDTShareAccessRule`

DESIGN 6.3 requires `Update-HDTBootImage` to run this and **warn loudly** when
the account is over-privileged, because "a domain admin credential in a boot
image is a domain compromise, and that is the failure worth catching".

```
Get-HDTShareAccessRule -Path <string> -> [object[]] { Identity, Rights, Type, IsInherited }
```
is the thin, untested adapter over `Get-Acl` (`.Access`, projected). It is the
only file in this plan that names `Get-Acl`.

```
Test-HDTShareAcl -WorkspaceRoot <string> -Identity <string>
                 -AccessRule <hashtable>   # folder relative path -> rule rows
    -> { Compliant [bool]; Finding [rows of { Path, Severity, Message }] }
```
is **pure logic** and is where every judgement lives. The expected posture, from
DESIGN 2.1 and 6.3:

| Folder | Expected for the deployment account |
|---|---|
| workspace root | Read only |
| `Logs\` | Write (or Modify) |
| `Captures\` | Write (or Modify) |
| everything else | no more than Read |

Findings, each its own test: `FullControl` anywhere → `Severity Critical`;
write anywhere but `Logs\` and `Captures\` → `Warning`; no read at the root →
`Critical` (the deployment cannot work); membership of a group whose name
matches `Domain Admins|Enterprise Admins|Administrators` in the identity list →
`Critical` with DESIGN 6.3's sentence quoted. `Compliant` is `$true` only when
there is no finding above `Information`.

It **never throws and never blocks a build.** DESIGN 6.3 says warn. A share whose
ACL cannot be read (a UNC the builder has no rights to) produces one
`Information` finding saying so, not a failure.
