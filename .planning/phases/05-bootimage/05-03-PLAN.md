### `bootstrap.json` — what the boot image carries, and the only file that tells the engine where it is

Written into the image at `X:\HDT\bootstrap.json` by `Update-HDTBootImage`
(05-04). **This plan defines and reads it; 05-04 writes it**, and 05-04 carries a
test that the file it writes is accepted by this reader.

```json
{
  "schemaVersion": 1,
  "workspaceId":   "HDT-LAB",
  "provider":      "Smb",
  "deployRoot":    "\\\\server\\HdtShare",
  "contentMarker": "rules.yaml",
  "sequenceId":    "",
  "credential":    { "username": "CONTOSO\\svc-hdt-deploy", "protected": "…" },
  "promptForCredential": false,
  "logLevel":      "Info",
  "buildId":       "…",
  "builtUtc":      "…"
}
```

```
Get-HDTBootstrapConfiguration -Path <string> [-FileSystem <object>]
```
reads through `IFileSystem`, parses with `ConvertFrom-Json`, validates, applies
defaults, returns a `[pscustomobject]`. Rules, each a failing test:

- `provider` outside `Smb|Local` → `HDTConfigurationError` naming the file, the
  value and the two;
- `deployRoot` missing or empty → error;
- `provider: Smb` with a `deployRoot` that is not UNC → error naming both;
- `credential` absent **and** `promptForCredential` false **and**
  `provider: Smb` → error saying the image was built without a credential and
  naming `-PromptForCredential`;
- `promptForCredential: true` → the credential block may be absent and the
  result reports `PromptForCredential $true`;
- a truncated / unparseable file → `HDTConfigurationError` naming the file. **Not
  a raw `ConvertFrom-Json` exception**: this file is read on a machine with no
  operator, and its failure is the last thing anyone will see;
- **`provider: Local` with a volume-relative `deployRoot` (`\Share`) is the form a
  boot image should carry, and it is legal.** SPIKES S9.1: WinPE gave the content
  disk `C:` and the RAM disk `X:`, so a letter written at build time is a guess
  about a machine that has not booted yet. `Resolve-HDTDeployRoot` turns it into
  a real path at boot; this reader only accepts it and hands it on;
- `contentMarker` defaults to `rules.yaml` and is the file that identifies a
  workspace root when the volume is discovered rather than configured;
- `provider: Local` with a **rooted** `deployRoot` is also legal - it is what a
  build host uses - and it is not an error for it to be absent at boot, because
  the resolver falls back to the probe;
- `sequenceId` empty is legal — the sequence then comes from the rules, which is
  DESIGN 3's answer to "which task sequence does this machine get".
- **Under Windows PowerShell 5.1 `ConvertFrom-Json` does not enumerate a
  top-level array and returns `PSCustomObject` for objects** — assign first, wrap
  second (helpers README F12; it bit 04-04 twice).

### `Resolve-HDTDeployRoot` — which drive is the content on?

**This is the difference between a boot image that deploys and a boot image that
sits there, and it is the one thing phase 04's launcher did that this plan had
dropped.** SPIKES S9.1: WinPE assigned the *content disk* `C:` and the RAM disk
`X:`; `Start-HDTLabDeployment.ps1` scanned `C D E F G H` for `HDT\Modules\Hephaestus`
for exactly that reason. This payload may not scan that way - it may not write a
letter down at all - and a `deployRoot` baked into `bootstrap.json` at build time
cannot know what WinPE will assign. So it does not pretend to.

```
Resolve-HDTDeployRoot -DeployRoot <string> -Provider <Smb|Local>
                      [-CandidateRoot <string[]>] [-Marker <string>]
                      [-FileSystem <object>]
    -> [pscustomobject] { Path, Source, Marker, Candidate [string[]] }
```

Pure logic, fully unit tested, and **the enumeration is deliberately not its
job**: the caller hands it candidates. That is what keeps the decision testable
and the payload thin, and it is the same split `Select-HDTTargetDisk` already
uses - the service enumerates, the function decides.

1. `Smb` -> `DeployRoot` unchanged, `Source = 'Configured'`. A UNC needs no
   volume.
2. `Local`, rooted (`D:\Share`), and `IFileSystem.TestPath` finds the marker under
   it -> unchanged, `Source = 'Configured'`.
3. `Local`, **volume-relative** (starts with one `\`, not two) -> for each candidate
   root **in the order given**, test the marker under
   `<candidate>` + `<DeployRoot>` — combined with `[IO.Path]::Combine` after the
   leading separator is trimmed off `DeployRoot`, so `D:\` plus `\Share` is
   `D:\Share` and not `D:\\Share`. First hit wins, `Source = 'Discovered'`. `-Marker` defaults to `rules.yaml`, DESIGN 3.3's
   file, which sits at the root of every workspace.
4. `Local`, rooted, but the marker is **not** there -> fall through to the same
   probe using the path's volume-relative form, and `Write-Warning` naming both.
   A boot image that was right yesterday should not be unbootable because a disk
   was added.
5. Nothing matched -> `HDTConfigurationError` naming the deployRoot, the marker,
   and **every candidate it looked at, in order**. That sentence is the last
   thing a machine with no operator will ever say, so it says everything a human
   needs to fix it.
6. More than one candidate matches -> the first wins and a `Warning` names all of
   them. Refusing would strand a machine over a stale second copy; silence would
   hide the ambiguity.

`Candidate` on the returned row is the list it searched, so `RESULT.json` can
record what it saw as well as what it chose - which is what a support call needs
when the answer was wrong.

### `Set-HDTLogPath` — DESIGN 4.4.1's relocation

```
Set-HDTLogPath -Context <logContext> -TargetVolume <string>
               [-Variable <IDictionary>]  -> [string] the new path
```

What it does, in order:

1. Compute the destination with `Get-HDTLogPath -Phase WinPE -TargetVolume`.
   **Do not build it by hand** — that function already owns the answer.
2. If the destination equals the current `Context.LogPath`, return it and do
   nothing. Idempotent, because the loop may ask more than once.
3. Create the destination through `Context.FileSystem`.
4. **Copy everything already written**, preserving the tree — `HDT.log`,
   `HDT.jsonl`, `status.json`, `Steps\`, `Gather\`, `Native\`. This is a mirror,
   not a move: the RAM-disk copy stays, because a relocation that deleted the
   only log and then failed would be worse than no relocation.
5. Repoint the context: `LogPath`, `JsonlPath`, `MasterLogPath`. **`Seq` is not
   touched** — DESIGN 4.4.2's counter is monotonic across the whole run and a
   reset here would be exactly the ambiguity it exists to prevent.
6. When `-Variable` is supplied, set `_HDTLogPath` in it. The engine variable is
   read-only *to sequences and rules*; the engine itself is what sets it, which
   is what the leading underscore means (DESIGN 4.4.1).
7. Write one `message` record naming **both** paths, through the *already
   repointed* context, so the first line in the new file explains why the file
   exists.
8. **It never throws.** A target volume that cannot be written — full, not
   formatted after all, a letter that went away — produces a `Warning` record
   through the old context, leaves everything pointing at `X:`, and returns the
   old path. Losing the logs is not an acceptable price for moving the logs.

### Where the loop triggers it

In `Invoke-HDTTaskSequence`, after each step's result is recorded and its
variables are published, and **only** when all four hold:

- `Context.Phase -eq 'WinPE'`;
- `Context.Variable['HDTOSVolume']` is now non-empty;
- the current `Log.LogPath` is still the RAM-disk path
  (`Get-HDTLogPath -Phase WinPE` with no target);
- the step just run reported `Completed`.

Then call `Set-HDTLogPath -Context $log -TargetVolume $osVolume -Variable $Context.Variable`.
One decision point, in the one place that sees every step finish.

### `Start-HDTDeployment.ps1` — the entry point

`src/Hephaestus/Payload/Start-HDTDeployment.ps1`. `Payload\` is not loaded by the
module (the loader dot-sources `Private\` and `Public\` only), so it ships as a
script and is staged to `X:\HDT\`, exactly as `Start-HDTResume.ps1` is staged to
`C:\HDT\`.

```
param(
  [string] $BootstrapPath = 'X:\HDT\bootstrap.json',
  [string] $ModuleRoot    = 'X:\HDT\Modules',
  [string] $SequenceId,                 # overrides the bootstrap and the rules
  [string] $LogRoot,                    # default Get-HDTLogPath -Phase WinPE
  [int]    $NetworkTimeoutSecond = 120
)
```

Thirteen things, in this order, and **nothing else**:

1. `Set-StrictMode -Version Latest`, `$ErrorActionPreference = 'Stop'`,
   `$InformationPreference = 'Continue'` (visible at the WinPE console without
   `Write-Host`, which the analyzer refuses).
2. Put `$ModuleRoot` on `PSModulePath`; import **`powershell-yaml` first**, then
   `Hephaestus`; log the version of each. The order is the dependency proof —
   `ConvertFrom-HDTYaml` reports `HDTDependencyError` without it and the engine
   cannot read one document.
3. Build the real adapters: `New-HDTFileSystem`, `New-HDTClock`,
   `New-HDTDiskService`, `New-HDTImageService`, `New-HDTRegistryService`,
   `New-HDTLsaService`, `New-HDTEnvironmentProvider`, `New-HDTCimProvider`,
   `New-HDTProcessService`, `New-HDTPowerService`, `New-HDTScriptInvoker`. **A
   fake never appears in this file.**
4. Build a log context at `$LogRoot` (default `X:\HDT\Logs`) **before** anything
   can fail, so step 5's failure is logged rather than printed and lost.
5. `Get-HDTBootstrapConfiguration`.
6. Wait for the network, but **only when `provider` is `Smb`**: poll
   `Get-HDTMachineFact`'s `HDTIPAddress` until it holds a non-APIPA IPv4 or
   `-NetworkTimeoutSecond` expires, logging each attempt. A `Local` provider does
   not wait, and that is the difference between a lab run starting in five
   seconds and starting in two minutes.
7. **Resolve the deploy root.** Enumerate candidate volumes with
   `[System.IO.DriveInfo]::GetDrives()`, filtered to `IsReady` and to `DriveType`
   `Fixed` or `Removable`, projected to `RootDirectory.FullName`. **That
   enumeration names no drive letter, and it is the only reason this file is
   allowed anywhere near one** (SPIKES S9.1). Hand the list, the bootstrap's
   `deployRoot`, `provider` and `contentMarker` to `Resolve-HDTDeployRoot`. Log
   the path it chose, its `Source`, and every candidate it considered — when this
   goes wrong on a machine nobody is watching, that log line is the whole
   investigation.
8. **The credential.** When `bootstrap.promptForCredential` is true, call
   `Get-Credential` and log at `Warning` that this image is deliberately **not**
   unattended. DESIGN 6.3 offers that build for a shared lab or media going
   offsite; it is the one path in this file that stops for a human, it must say
   so, and **the E2E never uses it**. When it is false, build the credential from
   the bootstrap's protected value. When `provider` is `Local`, neither happens.
9. `New-HDTContentProvider` with the **resolved** root; `Connect()`; log it.
   On refusal — including the guest refusal from 05-02 — log at `Error` and go
   straight to the `finally` with `Failed`.
10. `Get-HDTMachineFact` -> `Get-HDTMachineOverride` (keyed on `HDTUUID`) ->
    `Import-HDTRuleDocument` -> `Resolve-HDTVariable`, with the sequence's own
    defaults, exactly as `Start-HDTLabDeployment.ps1` already does. Which
    sequence: `-SequenceId`, else `bootstrap.sequenceId`, else the resolved
    `HDTTaskSequenceId` variable; **none of the three set is a named failure**,
    not a guess.
11. `New-HDTRunState`, `New-HDTExecutionContext` with a catalog that carries the
    **Content** provider.
12. **One** call to `Invoke-HDTTaskSequence`, with `-State`, `-StatePath` and
    `-LogDestination` pointing at `<deployRoot>\Logs`.
13. `finally`, in this order:
    - **write `RESULT.json` where it will still exist tomorrow.** The primary
      destination is `<resolved deployRoot>\Logs\RESULT.json`, built with
      `Get-HDTWorkspacePath -Kind Logs`, beside `LAUNCHER.log` — which is exactly
      where phase 04's stand-in wrote it, for the reason its comment gives: the
      harness must always know where to look, and a run that died before
      `Resolve-HDTVariable` has no computer name to nest under.
      **`X:\HDT\RESULT.json` is written as well, and it is the fallback, not the
      record** — `X:` is a RAM disk and the machine is about to be powered off,
      so a result written only there is a result nobody will ever read. **05-05's
      whole zero-keystroke proof reads `launchedBy` out of this file**, so where
      it lands is not a detail. When no deploy root was resolved the fallback is
      all there is, and that case says so in `message`. Both UTF-8 with no BOM,
      via `System.Text.UTF8Encoding` with `$false`;
    - `Copy-HDTLog` **again** unconditionally — the loop already does it when it
      got that far, and this is for the runs that did not;
    - `Disconnect()` the provider;
    - end the machine: `RebootPending` -> `wpeutil reboot`, anything else ->
      `wpeutil shutdown`. Record which one it used in `RESULT.json`'s `endedWith`:
      ROADMAP M2 left "does WinPE need `wpeutil reboot` rather than
      `shutdown.exe`" open, and this is the first run that can answer it.
    All of it after the `catch`, never inside the `try`.

**What this file must NOT do**, and the AST test enforces every line of it:
no Storage cmdlet, no DISM cmdlet, no `bcdboot`/`bcdedit`/`reagentc`/`diskpart`,
no `Invoke-HDT*Step`, no literal workspace folder name (`Get-HDTWorkspacePath`
owns those), no `New-HDTFake*`, **no drive letter written down other than `X:`**
(volumes are *enumerated*, never spelled — SPIKES S9.1), **no `Net*` cmdlet
WinPE does not have** (`Get-NetAdapter`, `Get-NetIPAddress`, `New-NetIPAddress`,
`Resolve-DnsName`, `Test-NetConnection` — DESIGN 5.1: there is no optional
component that adds them, and step 6 is exactly where somebody reaches for
one), no `Write-Host`, and **no technician UI** — DESIGN 11's progress window and wizard
are a later milestone and a silent entry point is the honest v1.

`RESULT.json` carries: `runId`, `status`, `failedStep`, `message`,
`computerName`, `sequenceId`, `provider`, `deployRoot`,
**`resolvedDeployRoot`**, **`deployRootSource`** (`Configured` or
`Discovered`), **`candidateRoot`** (every volume the resolver looked at),
`connected`, `yamlLoaded`, `yamlVersion`, `yamlBase`, `engineVersion`,
`psVersion`, `elapsedSecond`, `logPath`, `logDestination`, **`endedWith`**
(`wpeutil reboot` or `wpeutil shutdown`), and **`launchedBy`** — read from
`$env:HDT_LAUNCHED_BY`, which `startnet.cmd` sets (05-04) and a human typing the
command by hand does not. That single field is what 05-05 asserts to prove the
deployment started itself.
