### `New-HDTWdsService` — a dumb adapter that is not runnable here

```
GetBootImage([string] $Architecture)                      -> [object[]] { ImageName, Architecture, FileName, Version }
ImportBootImage([string] $Path, [string] $ImageName, [string] $Architecture) -> void
RemoveBootImage([string] $ImageName, [string] $Architecture)                 -> void
```
over `Get-WdsBootImage`, `Import-WdsBootImage -NewImageName -SkipVerify:$false`,
`Remove-WdsBootImage`. Its constructor **throws `HDTDependencyError` naming the
WDS module and the Windows Server role when the module is absent**, which is what
it does on this host and on any client OS. Branch-free otherwise (DESIGN 12.2.3).

It gets **no contract row against the real implementation**, and the contract
file says why in a comment: there is no WDS here, and standing one up is refused
by PROJECT.md.

### `Import-HDTBootImageToWds`

```
Import-HDTBootImageToWds -Path <string>
                         [-ImageName <string>] [-Architecture <x64|x86|arm64>]
                         [-WdsService <object>] [-FileSystem <object>]
                         -WhatIf -Confirm
```

`SupportsShouldProcess` — it removes a boot image a fleet PXE boots from.

Replace-in-place, and the ordered journal is the assertion:

1. refuse a `-Path` that is not an existing `.wim` — named error, no WDS call;
2. `-ImageName` defaults to the WIM's base name (`HDTPE_x64`);
3. `GetBootImage(<arch>)`;
4. when a row matches `ImageName` **case-insensitively**: `RemoveBootImage` then
   `ImportBootImage`. Log both at `Info`, naming the image being replaced and its
   previous version — an admin needs to know what was thrown away;
5. when no row matches: `ImportBootImage` only;
6. return `{ ImageName, Architecture, Path, Replaced [bool], PreviousVersion }`.

**The duplicate test is the point of the command** (ROADMAP M4: "WDS import
replacing rather than duplicating an existing image"): import twice against the
fake and assert `GetBootImage` reports **one** image, not two.

### `New-HDTPxePayload`

```
New-HDTPxePayload -WorkspaceRoot <string> -Path <string>
                  [-Architecture <string>] [-BootImageName <string>]
                  [-AdkRoot <string>] [-FileSystem] [-Registry]
                  -WhatIf -Confirm
```

DESIGN 6.1: "For sites with an existing TFTP/HTTP stack instead of WDS,
`New-HDTPxePayload` stages `bootmgr`, `bootmgfw.efi`, `boot.sdi`, the BCD, and
the boot WIM into a directory to point that server at."

**The required set is a declared table in the source**, and the test reads that
same table — so completeness is checked against one list rather than two:

| Destination | Source |
|---|---|
| `Boot\x64\bootmgr.exe` | ADK Media `bootmgr` |
| `Boot\x64\wdsmgfw.efi` *(when present)* | ADK Media `EFI\Boot\bootx64.efi` |
| `Boot\x64\bootmgfw.efi` | ADK Media `bootmgr.efi` |
| `Boot\x64\boot.sdi` | ADK Media `Boot\boot.sdi` |
| `Boot\x64\BCD` | ADK Media `Boot\BCD` |
| `Boot\x64\Fonts\*` | ADK Media `Boot\Fonts\*` |
| `Boot\x64\Images\<name>.wim` | `<workspace>\Boot\<name>.wim` |
| `Boot\x64\<name>.manifest.json` | `<workspace>\Boot\<name>.manifest.json` |

Returns one row per file: `Destination`, `Source`, `SizeBytes`, `Sha256`, and a
`Complete` boolean on the result object that is `$true` only when every
**required** row landed. Rows marked optional in the table (`wdsmgfw.efi`) do not
affect `Complete`, and the source comments say why: a site's TFTP stack may want
either name and this command does not know which.

- Refuse when `<workspace>\Boot\<name>.wim` is absent, naming
  `Update-HDTBootImage`.
- Refuse a `-Path` inside the workspace — the payload is for a different server.
- Everything through `IFileSystem`; every ADK path through `Get-HDTAdkPath`.
- Verify each copy by hash and report a mismatch as a failure, not a warning: a
  truncated `boot.sdi` on a TFTP server is a machine that hangs at boot with no
  message.

### The E2E — and what makes the zero-keystroke claim honest

Three independent proofs, because one would not be enough:

1. **The test file sends nothing.** `tests/unit/UnattendedDeploymentE2E.Tests.ps1`
   parses `tests/e2e/UnattendedDeployment.E2E.Tests.ps1` and asserts, over the
   comment-free token stream, that it names no `Send-HDTLabVmText`, no
   `TypeText`, no `TypeKey`, no `Msvm_Keyboard`. This runs in the **fast** suite,
   so the property cannot rot between lab runs. It is the same AST technique
   `StartHDTLabDeploymentPayload.Tests.ps1` uses, for the same reason: a claim a
   suite makes about itself must be checkable without running it.
2. **The guest says who started it.** `startnet.cmd` sets
   `HDT_LAUNCHED_BY=startnet` (05-04) and `Start-HDTDeployment.ps1` records it in
   `RESULT.json` (05-03). The E2E asserts `launchedBy -eq 'startnet'`. A
   hand-typed launch leaves it empty.
3. **The run would fail if nothing launched it.** Nothing types, so if
   `startnet.cmd` did not start the payload the VM sits at a WinPE prompt and
   `Wait-HDTLabVmState -State 'Off'` times out. There is no path where a silent
   failure looks like success — the same discriminator SPIKES S3 used when it
   proved the no-prompt ISO by giving the VM nothing else to boot from.

**Which provider the lab run uses, and the gap that leaves.** The VM sits on the
isolated `HDT Lab` switch (PROJECT.md rule 2), and SPIKES S6 records that a VM
there cannot reach a share on the host. So `bootstrap.json` in the image under
test declares **`provider: Local`** with a `deployRoot` on an attached content
disk, exactly as phase 04 did. **No VM in this phase deploys over SMB**, the
summary must say so in those words, and the Smb provider's evidence is 05-02's
unit refusals plus its loopback integration run. Do **not** move a test VM to
`HDT External` or `Default Switch` to close this gap.

**Deliverable 7's proof lands here.** After the machine has booted into Windows
and been stopped gracefully, the E2E mounts the deployed VHDX offline and asserts
`W:\HDT\Logs\HDT.jsonl` — the relocated WinPE log — **exists on the target
volume and contains the run's `run.start` record**. That file could not exist
without 05-03's relocation, and it is the difference between "the logs were
written" and "the logs survived".
