<objective>
Publish `HDTDeploymentMethod` where the provider is already known, and stop the
one behaviour that a disc has no answer for: the deploy-root retry ladder and
the Welcome screen behind it.

Purpose: `bootstrap.Provider` is baked into the boot image by
`Update-HDTBootImage` and read in `Start-HDTDeployment.ps1` around line 980,
where `Resolve-HDTDeployRoot` is already called with it. Setting the method
there puts it in front of the first step, so a step condition and the engine
gate on one value that cannot disagree with itself.

Output: the value in the run's variable bag and its provenance log, stamped by
the Tattoo step, and a connect loop that behaves differently under MEDIA — with
the SMB path unchanged and its existing tests untouched and green.
</objective>

<design_decisions>
**1. `Engine` joins the closed provenance source set.**
`Add-HDTResolvedVariable.ps1:109` carries
`[ValidateSet('CommandLine','Wizard','MachineOverride','Rule','RuleScript','GatheredFact','SequenceDefault')]`
and its own help says the set is closed *"because provenance is machine-readable"*
— closed, not frozen. `HDTDeploymentMethod` is none of those seven: it is not
gathered from the machine, it comes from the boot image the machine booted. The
honest answer is an eighth source, `Engine`, so the provenance log reads

    HDTDeploymentMethod = 'MEDIA' (Engine)

which is exactly what the phase asked the provenance log to say.

**Do not** smuggle it in as a `GatheredFact` by writing it into `$fact`.
`Invoke-HDTGatherStep` re-gathers facts mid-sequence and compares them against
what bootstrap resolved; a fact that `Get-HDTMachineFact` cannot produce would be
reported as *"could not be determined"* on every Gather step in every sequence.

**2. The value is computed once, early, as a local — and published twice.**
There are two readers at two different times in `Start-HDTDeployment.ps1`:

| Reader | Line, today | Needs |
|---|---|---|
| the connect loop (behaviour 1) | ~1129 | a plain local, because `Resolve-HDTVariable` has not run yet |
| `Get-HDTLogDestination` (behaviour 3, plan 03) | ~1390 | it in `$resolved.Variable` |
| the engine bag / state.json / steps | ~1694 | it in `$variable` |

So: compute `$deploymentMethod` at ~975, beside the `Resolve-HDTDeployRoot` call
that already has the provider; use the local in the connect loop; publish into
`$resolved` immediately after `Resolve-HDTVariable` returns; and set
`$variable['HDTDeploymentMethod']` beside the existing
`$variable['HDTDeploymentStart']` at ~1741. **One computation, three
publications, and an ordering test that proves the computation comes first.**

**3. It must survive the reboot.** `$variable` is what
`Invoke-HDTTaskSequence` checkpoints into `state.json`, and
`Start-HDTResume.ps1` puts the document back before it does anything. Publishing
into `$variable` therefore gives the full-OS leg the value for free — which plan
03 depends on. There is an assertion for it below.
</design_decisions>
