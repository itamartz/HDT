<verified_facts>
Probed on this machine on 2026-08-13, under pwsh 7.5.8 **and** Windows
PowerShell 5.1.26100.8655 unless stated.

**F1. `powershell-yaml` 0.4.12 imports and behaves identically on both
engines.** `ConvertFrom-Yaml` parses `true` to `[bool]`, `1` to `[int]`, and
leaves an unquoted `2026-08-13` as a `[string]`.

**F2. `-Ordered` is mandatory, not a nicety.** Without it the parser returns a
`[hashtable]` whose key order **differs between engines** — the same document
yielded `HDTSkipWizard, HDTJoinDomain, HDTCount` under pwsh and
`HDTCount, HDTJoinDomain, HDTSkipWizard` under 5.1. Since `set:` is applied in
document order, that difference would make variable resolution engine-dependent.
With `-Ordered` both engines return a
`System.Collections.Specialized.OrderedDictionary` in document order.

**F3. A YAML syntax error surfaces as
`System.Management.Automation.MethodInvocationException` whose
`InnerException` is `YamlDotNet.Core.SemanticErrorException`, and the inner
exception carries `.Start.Line` and `.Start.Column`.** Verified: line 4, column
4 for a mis-indented block. A duplicate mapping key throws the same way with the
message `Duplicate key a`. This is what makes "name the file **and the line**"
achievable.

**F4. An empty document parses to `$null`,** it does not throw.

**F5. `Test-Json` exists under pwsh 7 and does NOT exist under Windows
PowerShell 5.1.** So JSON Schema validation is a CI/authoring-side gate, and the
engine's own validator is what runs in WinPE. The schema contract test must skip
under 5.1 with an explicit reason.

**F6. `Test-Json -Schema` (draft-07) correctly rejects** an unknown rule key, a
rule with neither `set` nor `setFrom`, and a `set` key named `_HDTLogPath`.
Its *message* names the failing `anyOf` branch rather than the real problem, so
the schema is a gate, not the source of the message a user reads. The engine's
own `Assert-HDTRuleDocument` message is the one that matters.

**F7. `[System.Management.Automation.ErrorRecord]::new($exception, $errorId,
$category, $target)` thrown with `$PSCmdlet.ThrowTerminatingError()` produces
`FullyQualifiedErrorId = 'HDTConfigurationError,<FunctionName>'` on both
engines,** with `CategoryInfo.Category` and `TargetObject` preserved. Tests
assert on the captured record, not on Pester's `-ErrorId` matching semantics.

**F8. `[System.Collections.Specialized.OrderedDictionary]::new([System.StringComparer]::OrdinalIgnoreCase)`
works on both engines** and gives ordered, case-insensitive lookup. Every
dictionary this plan hands to plan 02-03 is built that way.
</verified_facts>

### Signatures

```
New-HDTErrorRecord -Message <string> [-Path <string>] [-Line <int>]
                   [-ErrorId <string> = 'HDTConfigurationError']
                   [-Category <System.Management.Automation.ErrorCategory> = 'InvalidData']
                   [-InnerException <System.Exception>]
    -> [System.Management.Automation.ErrorRecord]

ConvertFrom-HDTYaml -Yaml <string> -Path <string>
    -> [System.Collections.Specialized.OrderedDictionary] | $null
```

Message composition, exactly:
- with `-Line`: `"{Path}({Line}): {Message}"`
- with `-Path` only: `"{Path}: {Message}"`
- with neither: `"{Message}"`

`-Path` also becomes the `TargetObject`. Every caller throws with
`$PSCmdlet.ThrowTerminatingError((New-HDTErrorRecord ...))` (F7) — never
`throw "string"`, because a bare string loses the error id and the target that
make these errors greppable in a log.

`ConvertFrom-HDTYaml` is the **only** place in the engine that mentions
`ConvertFrom-Yaml`. It:
1. ensures the dependency: if `Get-Command ConvertFrom-Yaml` finds nothing,
   `Import-Module powershell-yaml -ErrorAction Stop`; if that fails, throw with
   `-ErrorId 'HDTDependencyError' -Category NotInstalled` and a message naming
   the module and `Install-Module powershell-yaml`;
2. calls `ConvertFrom-Yaml -Yaml $Yaml -Ordered` (F2 — never without `-Ordered`);
3. catches, walks to the innermost exception, reads `.Start.Line` when the
   inner exception exposes it (F3), and rethrows as a configuration error whose
   message is
   `"the YAML in this file could not be parsed. <parser message>"` prefixed by
   path and line by `New-HDTErrorRecord`.

**Do not add `powershell-yaml` to the manifest's `RequiredModules`.** It would
make the module unimportable wherever the dependency is missing and would
complicate WinPE staging. The lazy import above is the contract; record in the
SUMMARY that **phase 05 must stage `powershell-yaml` into the boot image**,
because WinPE has no gallery.
