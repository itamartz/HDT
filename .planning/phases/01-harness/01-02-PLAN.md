<verified_ast_facts>
Probed on this machine — build the implementation on these, do not re-derive:

**Windows PowerShell 5.1 `[Parser]::ParseInput` results:**

| Sample | 5.1 parse errors |
|---|---|
| `$b = $a ?? 'x'` | 1 — `Unexpected token '??' in expression or statement.` |
| `$c = ${a}?.Length` | 1 — `Unexpected token '?.Length' ...` |
| `$d = $true ? 1 : 2` | 1 — `Unexpected token '?' ...` |
| `1..2 \| ForEach-Object -Parallel { $_ }` | **0 — parses fine** |
| `function f { clean { 1 } }` | **0 — parses fine** |

So under 5.1 the first three are caught as *parse errors*; `-Parallel`,
`clean`, `Get-Error`, `$PSStyle` and `ConvertFrom-Json -AsHashtable` must be
caught by AST/token inspection, which works on both engines.

**pwsh 7.5 token kinds / AST types produced:**

| Syntax | Detect via |
|---|---|
| `??` | token `Kind.ToString() -eq 'QuestionQuestion'` |
| `??=` | token `'QuestionQuestionEquals'` |
| `${a}?.Member` | token `'QuestionDot'` (also `MemberExpressionAst.NullConditional -eq $true`) |
| `@(1,2)?[0]` | token `'QuestionLBracket'` (also `IndexExpressionAst.NullConditional -eq $true`) |
| `$a ? 1 : 2` | AST `GetType().Name -eq 'TernaryExpressionAst'` |
| `clean {}` | `ScriptBlockAst` where `PSObject.Properties.Name -contains 'CleanBlock'` **and** `$_.CleanBlock -ne $null` |

**Gotcha:** `$a?.Length` (unbraced) does NOT produce a `QuestionDot` token —
`?` is a legal variable-name character, so it parses as variable `$a?`. Braced
`${a}?.Length` does. Fixtures must use the braced form for the null-conditional
cases, and the implementation must not rely on unbraced detection.

**Cross-version safety rule:** never write `[System.Management.Automation.Language.TernaryExpressionAst]`
or `[TokenKind]::QuestionQuestion` as a type/enum literal — those do not exist
under 5.1 and would make the test file itself unparseable. Compare
`GetType().Name` and `Kind.ToString()` as **strings**.
</verified_ast_facts>

<design_correction>
**DESIGN §15.1 states the regex `^[A-Z][a-z]+-HDT[A-Z]` and, three lines above,
lists `ConvertTo-HDTReport` as a valid name. Those contradict**: `[A-Z][a-z]+`
cannot match `ConvertTo` (capital `T` mid-verb). The same applies to any
two-word approved verb — `ConvertFrom`, `ForEach`, `WaitFor`.

Resolution, to be implemented and recorded:
- The enforced pattern is **`^([A-Z][a-zA-Z]*)-HDT[A-Z][A-Za-z0-9]*$`**, matched
  **case-sensitively** (`-cmatch`), so `Get-HdtThing` and `get-HDTThing` fail.
- Plus: the verb segment must appear in `Get-Verb` with exact case.

The verb check is the real constraint; the widened regex just stops the pattern
from rejecting names DESIGN itself blesses. Task 3 updates DESIGN §15.1 to state
the corrected pattern and one sentence of rationale.
</design_correction>
