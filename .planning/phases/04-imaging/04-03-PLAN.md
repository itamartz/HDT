### One rule that shapes all five steps

**A step never lets a refusal escape as a terminating error.** It catches it,
logs `step.fail`, and returns

```powershell
New-HDTStepResult -Status Failed -Message $refusal.Exception.Message `
    -Data ([ordered] @{ errorId = 'HDTAmbiguousTargetError'; disk = @(...) })
```

so the step contract holds. To keep 04-02's "a refusal is never retried"
property, this plan extends the classifier:

```
Get-HDTFailureClass [-ErrorRecord <object>] [-ResultData <object>] [-TimedOut]
```

A `ResultData` carrying an `errorId` in the configuration list
(`HDTConfigurationError`, `HDTAmbiguousTargetError`, `HDTUnsafeTargetError`,
`HDTNoTargetDiskError`, `HDTAmbiguousImageError`) classifies as `Configuration`.
`Invoke-HDTStepAttempt` passes `-ResultData $result.Data`. Two tests, one at the
classifier and one at the loop ("does not retry a step that refused for a
configuration reason, even when the step declares retry: 2").

### `Get-HDTStepProperty` — the shared reader (private)

```
Get-HDTStepProperty -Step <object> -Name <string> [-Default <object>]
                    [-Context <object>] [-Expand] [-As <string>]
  -> the value, expanded and coerced
```

`-Expand` runs `Expand-HDTVariableToken` against `$Context.Variable`, because
every property in the sample sequence is written `"%HDTOSImage%"`. `-As` coerces
to `String`, `Int`, `Long` or `Bool`, throwing a configuration error naming the
step and the property when the value will not convert — an authoring mistake
should say `index: abc is not a number on step 'Apply OS'`, not
`Cannot convert value`. All five steps read every property through it; none of
them touches `$Step.Property` directly.

### The variables the steps publish

Written into `$Context.Variable` so later steps and conditions compose. All are
writable `HDT*` names, added to `Get-HDTVariableMap` with a description — the
`VariableNamespace` contract requires every mapped name to carry one, and
requires every non-underscore name to be writable.

| Variable | Set by | Meaning |
|---|---|---|
| `HDTTargetDisk` | `DiskPartition` | the disk number that was partitioned |
| `HDTSystemVolume` | `DiskPartition` | the ESP / System Reserved drive letter (`S`) |
| `HDTOSVolume` | `DiskPartition` | the Windows drive letter (`W`) |
| `HDTRecoveryVolume` | `DiskPartition` | the recovery drive letter (`R`), or empty |
| `HDTOSImage` | sequence | the catalog id, already used by the sample |
| `HDTImageIndex` | `ApplyImage` | the index that was applied |
| `HDTUnattendPath` | `ApplyUnattend` | where the unattend was staged |

MDT counterparts, for the map's MDT column: `OSDDiskIndex`, `BootVolume`,
`OSVolume`, `RecoveryVolume`. `HDTOSImage`, `HDTImageIndex` and
`HDTUnattendPath` have none and take `$null`.

### `Validate`

```yaml
- name: Validate
  type: Validate
  minRamMB: 2048
  minDiskGB: 60
  requireUefi: true          # optional
  diskNumber: 0              # optional, mirrors DiskPartition
  requireVariable: [HDTComputerName]   # optional
```

Reads `HDTMemory` and `HDTIsUEFI` from the context variables (gathered facts, not
CIM — the step may not touch CIM), and the disks through `IDiskService`. It runs
`Select-HDTTargetDisk` with the same arguments `DiskPartition` will, so a
deployment that is going to refuse **refuses in the first step**, before anything
destructive, which is the whole point of a pre-flight.

Returns `Completed` when every check passes; otherwise `Failed` whose message
lists **every** failed check, not the first.

### `DiskPartition` — the destructive one

```yaml
- name: Format and Partition
  type: DiskPartition
  layout: "%HDTDiskLayout%"    # optional; firmware decides otherwise
  wipe: true                   # required for a disk that is not RAW
  diskNumber: 0                # optional; the ambiguity override
  minDiskGB: 60                # optional; default 60
```

`[CmdletBinding(SupportsShouldProcess = $true)]`, and
`$PSCmdlet.ShouldProcess("disk $n ($friendlyName, $sizeGB GB)", 'Clear and repartition')`
gates every write. Under `-WhatIf` it plans, logs the plan and returns
`Completed` having called no write method — DESIGN 15.2 and PROJECT constraint 5.

The order, which is SPIKES S6's verified recipe and is asserted from the journal:

1. `GetDisk`, `GetPartition`, `GetVolume`.
2. `Select-HDTTargetDisk`, always passing **`-ProtectDriveLetter`** built from
   the drive letters of `$Context.WorkspaceRoot` and `$Context.Log.LogPath`, so
   HDT cannot wipe the disk it is reading its instructions from or writing its
   log to. `-AllowExistingData` comes from `wipe: true`.
3. `Resolve-HDTDiskLayoutName` → `Get-HDTDiskLayout` → `New-HDTDiskLayoutPlan`.
4. `ClearDisk`.
5. `InitializeDisk` with the layout's style. **No MSR is created** — the comment
   in the file names SPIKES S6 and `PSDPartition.ps1`.
6. Per planned partition, in order: `NewPartition` (with `CreateGptType` where
   the layout has one) → `SetPartitionDriveLetter` → `FormatVolume` →
   `SetPartitionType` where the layout's final type differs from the created one.
7. Publish `HDTTargetDisk`, `HDTSystemVolume`, `HDTOSVolume`,
   `HDTRecoveryVolume`.

### `ApplyImage`

```yaml
- name: Apply OS
  type: ApplyImage
  os: "%HDTOSImage%"         # catalog id  ... or image: an explicit path
  index: 1                   # or name:/edition:
  target: primary            # 'primary' = %HDTOSVolume%, or a drive letter
  timeoutMinutes: 60
```

`Get-HDTOperatingSystem` → `Resolve-HDTImageIndex` → `IImageService.ApplyImage`.
The apply root is `<HDTOSVolume>:\` unless `target` names a letter; a `target`
that resolves to nothing is a `Failed` result naming the variable, **never** a
guess at `C:`. Logs `native.exec` with the WIM, the index and the target at
Info, and the elapsed time on completion (SPIKES S6 measured 95 s for 4 GB over
SMB, so the duration is worth having in the log). Publishes `HDTImageIndex`.

### `ApplyUnattend`

```yaml
- name: Apply Unattend
  type: ApplyUnattend
  template: unattend.xml     # relative to the sequence folder, or rooted
  target: "%HDTOSVolume%"    # optional
  expand: true               # optional, default true
```

Reads the template through `IFileSystem`, expands `%Var%`, creates
`<target>:\Windows\Panther` and writes `unattend.xml` there — **the S7-verified
location**. Publishes `HDTUnattendPath`.

The template path resolves through `Get-HDTWorkspacePath -Kind TaskSequences
-ChildPath <sequenceId>, <template>` when it is relative, and is used as given
when it is rooted. No literal `'TaskSequences'` anywhere.

**Secrets.** The expansion may substitute `HDTAdminPassword`, and when the run
state carries a `deploymentPassword` and the template names
`%HDTAdminPassword%` with no such variable resolved, the step uses the
deployment password (DESIGN 4.5.1: the `oobeSystem` `AutoLogon` block is what
arms the first logon). The step logs the **path and the byte count only**; the
expanded document is never logged at any level, and a test asserts the password
appears nowhere in `HDT.jsonl`, `HDT.log` or the step log — the same assertion
03-05 makes about the report.

### `ConfigureBoot`

```yaml
- name: Prepare Boot
  type: ConfigureBoot
  firmware: auto             # auto | UEFI | BIOS
  recovery: true             # optional; default true when a recovery volume exists
  setBootOrder: true         # optional; default true
```

1. `InstallBootFile("<HDTOSVolume>:\", "<HDTSystemVolume>:", 'UEFI'|'BIOS')` —
   `auto` reads `HDTIsUEFI`.
2. When `recovery` and `HDTRecoveryVolume` is set: create
   `<R>:\Recovery\WindowsRE`, copy
   `<W>:\Windows\System32\Recovery\Winre.wim` into it through `IFileSystem`, then
   `SetRecoveryImage`. A missing `Winre.wim` is a **warning and a skip**, not a
   failure: an image without WinRE still boots, and failing the deployment over
   it would be worse than the gap.
3. When `setBootOrder`: `SetBootOrderFirst()`. **This is SPIKES S6's fourth
   finding**, and the comment in the file says so: without it the machine
   reboots into the installation media and the deployment appears to loop.
