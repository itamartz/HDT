<objective>
Make a media definition a thing that exists on a share: `Media\<id>\media.yaml`,
a validator that knows its keys, a JSON Schema beside it, and the four commands
that create, read, edit and delete one.

This plan builds NOTHING. It does not project a share, does not touch the ADK
and does not burn an ISO — plan 02 does all three. What it produces is the
persisted object MDT's Deployment Workbench has under Advanced Configuration:
a media item with a selection profile and an output path, which
`Update-HDTMediaContent` then regenerates.

Purpose: the document has to exist and has to be *known to every surface that
enumerates documents* before anything reads it. A validator that does not know a
key makes the key invisible, and this repository has shipped that half-feature
twice (CLAUDE.md rule 8).

Output: `New-HDTMedia`, `Get-HDTMedia`, `Set-HDTMedia`, `Remove-HDTMedia`,
`Assert-HDTMediaDocument`, `schemas/media.schema.json`, a `Media` folder on every
new share, and the manifest/reference/bundle updates that make each real.
</objective>

**`docs/DESIGN.md` §6.2 "Standalone media", rewritten 2026-09-03.** It settles:

**MDT's shape, which is the one being copied** (CLAUDE.md: check MDT, then PSD,
then ask). Deployment Workbench has a **Media** node under **Advanced
Configuration**. A media item carries a **selection profile** (defaulted to
Everything), a **media path**, an **enabled** tick, and an **Update Media
Content** action that regenerates it. That is the whole object. HDT builds the
same object, as YAML, under `Media\<id>\`.

**The per-item document family already here.** `Applications\<id>\app.yaml` is
the closest prior art and the pattern to follow exactly:
`Get-HDTApplication` reads one or all, validates with
`Assert-HDTApplicationDocument`, projects with `ConvertTo-HDTApplicationCatalog`,
and adds `WorkspaceRoot` to the returned object so a pipeline into `Set-` or
`Remove-` works. `Remove-HDTApplication` is the destructive one and it makes
**two separate checks** — the id as typed, then the path it resolved to — which
is the shape `Remove-HDTMedia` must copy.

**The layout is written down once.** `Get-HDTWorkspacePath`'s `-Kind`
`ValidateSet` is the ONLY place the share's folder names live.
`New-HDTWorkspace.ps1:172` and `Test-HDTShareAcl.ps1:110` both read it by
reflection. Adding `Media` there creates the folder on every new share and
ACL-checks it, with no second edit anywhere — which is what rule 8 asks for and
is why this is done first.
</evidence>

<design_decisions>
Six calls this plan makes, stated once here so the tasks can be short. Each is
made from `docs/DESIGN.md` §6.2 and the MDT shape above; none needs confirming.

**1. The key set is seven, and no more.**

```yaml
schemaVersion: 1
id: WIN11-FIELD
name: Windows 11 field media
description: Engineers' laptop build, no network
selectionProfile: everything
output: Media\WIN11-FIELD\HDT_WIN11-FIELD.iso
enabled: true
```

`id`, `name`, `selectionProfile`, `output` and `enabled` are what the console
shows and the build reads; `description` is what MDT's Comments box is;
`schemaVersion` is what every HDT document declares. Nothing else earns a key.

**2. `selectionProfile` defaults to `everything`, because MDT's does.** A media
item with no profile named is a whole share on a disc, which is the answer
somebody making standalone media wants first. The built-in ids come from
`Get-HDTSelectionProfileBuiltIn`; an authored one comes from
`Control\selection-profiles.yaml`.

**3. `output` is share-relative unless it is rooted**, and the default is
`Media\<id>\HDT_<id>.iso`. A relative path resolves against the workspace root at
READ time (in `ConvertTo-HDTMediaCatalog`), never at write time — the share is
routinely authored on one machine and built on another, so a path expanded to a
letter at creation is the one value that is certainly wrong. This is the same
rule `Update-HDTBootImage` follows for `deployRoot`.

**4. `enabled` exists and is a refusal, not a filter.** MDT's media item has the
tick and `Update-HDTMediaContent` must honour it: a disabled item is refused by
name, telling the administrator to run `Set-HDTMedia -Enabled` — rather than
skipped silently, which reads as a build that did nothing.

**5. The last build is a MANIFEST beside the ISO, not a key in media.yaml.**
`Media\<id>\media.manifest.json`, written by plan 02, exactly as
`Boot\<name>.manifest.json` already works. Two reasons, and both are already
written down in this repository: `media.yaml` is a file an administrator
hand-edits and comments, and a build that rewrote it every run would either lose
those comments or need a splice for a value nobody types; and a manifest on disk
means the artifact beside it came from the build that wrote it. `Get-HDTMedia`
READS the manifest when it is there and reports `LastBuildUtc`, `IsoPath`,
`IsoSizeBytes` and `IsoSha256` as `$null`/empty when it is not.

**6. There is no `New-HDTMediaDocument`/`Save-` split.** The selection-profile
family splits them because one document holds every profile and the console
edits it as lines. A media item is a document of its own, like `app.yaml`, so
`New-HDTMedia` writes the file through `IFileSystem` and `Set-HDTMedia` splices
it in place — which is what `Set-HDTApplication` and `Set-HDTTaskSequenceProperty`
already do.
</design_decisions>
