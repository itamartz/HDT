# Phase 05 Plan 06: the WinPE power question, answered by execution

## Why this plan exists

`docs/ROADMAP.md` M2 left one question open and named phase 05 as its owner:

> **`New-HDTPowerService` has never been executed** and whether WinPE needs
> `wpeutil reboot` rather than `shutdown.exe` is a phase 05 question.

`05-VERIFICATION.md` records it as `not_answered` after five plans.
`New-HDTPowerService.ps1` and `PowerService.Contract.Tests.ps1` both carry the
comment *"UNVERIFIED, RECORDED FOR PHASE 05"*. Phase 05 may not close with its
own named question still open when the answer is one mount away.

A reconnaissance mount of the boot image `Update-HDTBootImage` built in 05-04
(`C:\HDTLab\scratch\bootimage\Share\Boot\HDTPE_x64.wim`, read-only, discarded):

```
shutdown.exe     False
wpeutil.exe      True    32768
wpeinit.exe      True    61440
```

**`shutdown.exe` is not in the image at all.** So this is not a question of
style: `New-HDTPowerService` defaults to `shutdown.exe`, the engine's `Restart`
step calls it through `IPowerService`, and in WinPE that call cannot resolve a
command. A `Restart` step in a WinPE sequence would have failed on the first
machine that ran one. Nothing caught it because `DEMO-M3` and `DEMO-M4` both
deliberately have no `Restart` step, and the contract's real row is skipped.

## Tasks

### Task 1 — `Get-HDTPowerCommand`, the pure decision (tdd)

Private, pure, no environment reads, no invocation.

    Get-HDTPowerCommand -Environment WinPE|FullOS -Operation Restart|Stop -DelaySecond <int>

returns `Environment`, `Operation`, `Command`, `Argument` (string[]),
`SleepSecond`, `Reason`.

- **FullOS** -> `shutdown.exe` `/r|/s /t <delay> /f`, `SleepSecond` 0: the
  command owns the delay.
- **WinPE** -> `wpeutil.exe` `reboot|shutdown`, `SleepSecond` = the delay:
  `wpeutil` has no delay verb, so the only honest way to honour one is to sleep
  first, and the object says so rather than dropping it.
- A negative delay is refused by name.

### Task 2 — the adapter, and the two callers that already know (tdd)

- `New-HDTPowerService -Environment <WinPE|FullOS>`, **mandatory**. A default
  is what produced the defect: every existing caller would have kept the wrong
  one.
- `Restart` / `Stop` call the pure function, `Start-Sleep` unconditionally
  (`-Seconds 0` is a no-op, so there is still no branch), then invoke. The
  recorded operation and its arguments are unchanged, so every journal
  assertion in phases 03-05 still means what it meant.
- `Start-HDTDeployment.ps1` passes `WinPE`; `Start-HDTResume.ps1` passes
  `FullOS`. Both already hardcode their phase; neither needs detection.
- Asserted by AST in the payload test files, and by a test that the payload's
  own final `wpeutil` line agrees with what `Get-HDTPowerCommand` yields - so
  the two cannot drift.

### Task 3 — the evidence, and the first real execution (tdd)

- `tests/integration/WinPeContent.Integration.Tests.ps1`: mounts the real ADK
  `winpe.wim` read-only and asserts `wpeutil.exe` present and `shutdown.exe`
  **absent**. This is the fact the whole decision rests on, and it will say so
  the day Microsoft changes it.
- `tests/e2e/WinPeSmoke.E2E.Tests.ps1` + `tests/e2e/payload/Start-HDTLabProbe.ps1`:
  the smoke VM is powered off **by `New-HDTPowerService -Environment WinPE`**
  rather than by a direct `wpeutil` call. The probe writes `PROBE.json` first,
  invokes the service, and only after a bounded wait falls back to a direct
  `wpeutil shutdown` leaving `FALLBACK.txt` behind. **The assertion is that
  `FALLBACK.txt` is absent**, which is what makes "the service did it" a fact
  rather than a coincidence of a machine that was going to power off anyway.
