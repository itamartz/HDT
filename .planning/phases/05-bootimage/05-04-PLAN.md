### `IBootImageService` — nine methods, and it is an untested adapter

```
MountImage([string] $ImagePath, [int] $Index, [string] $MountPath)      -> void
DismountImage([string] $MountPath, [bool] $Save)                        -> void
AddPackage([string] $MountPath, [string] $PackagePath)                  -> void
AddDriver([string] $MountPath, [string] $DriverPath, [bool] $Recurse)   -> [object[]] the drivers added
GetPackage([string] $MountPath)                    -> [object[]] { Name, State }
GetImageInfo([string] $ImagePath)                  -> [object[]] { Index, Name, SizeBytes }
ExportImage([string] $SourcePath, [int] $Index, [string] $DestinationPath) -> void
SetScratchSpace([string] $MountPath, [int] $Megabyte)                   -> void
NewIso([string] $MediaRoot, [string] $IsoPath, [string[]] $Argument)    -> void
```

| Method | Mechanism |
|---|---|
| `MountImage` | `Mount-WindowsImage -ImagePath -Index -Path` |
| `DismountImage` | `Dismount-WindowsImage -Path -Save` / `-Discard` |
| `AddPackage` | `Add-WindowsPackage -Path -PackagePath` |
| `AddDriver` | `Add-WindowsDriver -Path -Driver [-Recurse]` |
| `GetPackage` | `Get-WindowsPackage -Path` |
| `GetImageInfo` | `Get-WindowsImage -ImagePath` |
| `ExportImage` | `Export-WindowsImage -SourceImagePath -SourceIndex -DestinationImagePath -CompressionType Max` |
| `SetScratchSpace` | `dism.exe /Image:<mount> /Set-ScratchSpace:<mb>` — there is no cmdlet |
| `NewIso` | `oscdimg.exe @Argument <MediaRoot> <IsoPath>` |

`ExportImage` with `-CompressionType Max` is DESIGN 5.1's `/Compress:max`.

**`NewIso` takes the argument array already built.** All the decisions —
firmware, no-prompt, the space-free staging — live in
`Get-HDTBootIsoArgument`, which is pure string logic and therefore fully tested.
The adapter runs the process and checks `$LASTEXITCODE`, attaching oscdimg's own
output on failure. That is the DESIGN 12.2.3 line, and this adapter is on the
untested side of it: nine of its methods mount, write or burn.

`[pscustomobject]` with `ScriptMethod` members (helpers README 11), `-Journal`,
`Operations`, `GetOperationName()`, `ServiceName = 'BootImageService'`, records
before the call can throw, array returns use the unary comma (F3).

**The fake models a mount.** `New-HDTFakeBootImageService` is given an
`IFileSystem` and, on `MountImage`, seeds `<MountPath>\Windows\System32\` into it
so the builder can write `startnet.cmd` to a path that exists, and so a test can
read back exactly what the builder wrote. `DismountImage($false)` must make the
mount path's contents unreadable, so a builder that wrote after discarding is
caught.

### `Get-HDTStartnetScript`

Pure. Returns the exact text `Update-HDTBootImage` writes to
`<mount>\Windows\System32\startnet.cmd`:

```
@echo off
rem Written by Update-HDTBootImage. Do not edit inside the image; edit HDT.
set HDT_LAUNCHED_BY=startnet
wpeinit
powershell.exe -NoProfile -ExecutionPolicy Bypass -File X:\HDT\Start-HDTDeployment.ps1
```

Five lines and no more. Each one is its own assertion:

- `wpeinit` runs **before** PowerShell — it is what brings up networking, and a
  share connect before it would fail on a machine that was going to work;
- `X:` is written literally, and it is the only drive letter allowed here,
  because the RAM disk is the one letter WinPE guarantees (SPIKES S9.1);
- `HDT_LAUNCHED_BY=startnet` is the field `Start-HDTDeployment.ps1` records into
  `RESULT.json` and **05-05 asserts to prove nobody typed the command**;
- no drive scan, no `for %d in (...)` — that loop exists in the phase-04 harness
  only because a human was typing it;
- the file is written as **ASCII with no BOM**, and a test asserts the first byte
  is not `0xEF`. `cmd.exe` reading a BOM as a command is a class of failure that
  produces no useful message at all.

`-Command <string>` overrides the last line for a caller that wants a different
entry point (standalone media, a diagnostic image); the default is the one above.

### `Get-HDTBootIsoArgument`

```
Get-HDTBootIsoArgument -Firmware <UEFI|BIOS|Both> [-NoPromptForKey]
                       -BootBitPath <string> [-Label <string>]
    -> [string[]]
```

Pure, and it is where SPIKES S2 lives:

- **refuses a `-BootBitPath` containing a space**, with a message naming SPIKES
  S2 and the verified error (`Could not open boot sector file ""C:\Program
  Files (x86)\...\etfsboot.com""`). The caller stages the bits; this function
  refuses to build an argument that is known not to work;
- the fixed head is `-m -o -u2 -udfver102`, plus `-l<Label>` when a label was
  given (`HDTPE_x64` by default, uppercased, no spaces — an ISO label with a
  space is its own class of trouble);
- the `-bootdata` element, one string, **unquoted inside**:

  | Firmware | NoPromptForKey | `-bootdata` |
  |---|---|---|
  | UEFI | yes | `1#pEF,e,b<bits>\efisys_noprompt.bin` |
  | UEFI | no | `1#pEF,e,b<bits>\efisys.bin` |
  | BIOS | yes | `1#p0,e,b<bits>\etfsboot.com` **+ warning** |
  | BIOS | no | `1#p0,e,b<bits>\etfsboot.com` |
  | Both | yes | `2#p0,e,b<bits>\etfsboot.com#pEF,e,b<bits>\efisys_noprompt.bin` **+ warning** |
  | Both | no | `2#p0,e,b<bits>\etfsboot.com#pEF,e,b<bits>\efisys.bin` |

- **the warning text is specified, not left to the author**: for `BIOS`,
  *"-NoPromptForKey has no effect on a BIOS boot: etfsboot.com carries the
  'Press any key' prompt in its boot sector and Microsoft ships no no-prompt
  variant. This ISO will prompt when booted on BIOS firmware."* For `Both`, the
  same sentence with *"…on the BIOS leg only; the UEFI leg will not prompt."*
  DESIGN 5.2: "HDT states this rather than pretending otherwise."

### `New-HDTBootIso`

```
New-HDTBootIso -MediaRoot <string> -Path <string>
               [-Firmware <UEFI|BIOS|Both>]   # default UEFI
               [-NoPromptForKey]
               [-Label <string>] [-BootBitPath <string>]
               [-AdkRoot <string>] [-Architecture <string>]
               [-BootImageService] [-FileSystem] [-Registry]
               -WhatIf -Confirm
```

1. Resolve `Oscdimg`, `EtfsBoot`, `EfiSys`, `EfiSysNoPrompt` with
   `Get-HDTAdkPath` — never a literal.
2. **Stage** the two or three bits it needs into `-BootBitPath` (default
   `$env:SystemDrive\HDTBootBits`, which has no space by construction). Create
   it, copy, and say in a comment that this exists because of SPIKES S2 and not
   for tidiness.
3. `Get-HDTBootIsoArgument`.
4. `ShouldProcess` on the ISO path — it overwrites a file.
5. `NewIso`.
6. Return a row: `Path`, `SizeBytes`, `Firmware`, `NoPromptForKey`, `Label`,
   `MediaRoot`, `Sha256`.

Default `-Firmware UEFI` (DESIGN 5.2: Gen2 and every modern physical machine).
`-NoPromptForKey` is a switch and defaults **off** for a direct caller;
`Update-HDTBootImage` passes it **on** unless `-PromptForKey` was given, which is
DESIGN 5.2's "on for `New-HDTBootIso` invoked by `Update-HDTBootImage`, because a
boot image you mount to test something should just boot".

### `Update-HDTBootImage`

```
Update-HDTBootImage -WorkspaceRoot <string>
                    [-OptionalComponent <string[]>]     # overrides workspace.yaml
                    [-Architecture <string>] [-Language <string>]
                    [-SkipIso] [-PromptForCredential] [-PromptForKey]
                    [-Firmware <UEFI|BIOS|Both>]
                    [-ScratchPath <string>]             # default C:\HDTLab\scratch\bootimage
                    [-BootImageService] [-FileSystem] [-Registry] [-Clock]
                    -WhatIf -Confirm
```

`SupportsShouldProcess`, because it replaces `Boot\HDTPE_x64.wim` and
`Boot\HDTPE_x64.iso` — artifacts a fleet PXE boots from.

**Seventeen steps, and the fake's journal asserts this exact order:**

1. `Import-HDTWorkspaceDocument`.
2. `Get-HDTAdkPath -All`; refuse with one sentence when anything needed is
   missing.
3. `Get-HDTBootImageComponent`, with `-OptionalComponent` overriding the
   document's list when given.
4. Prepare scratch: `<scratch>\mount`, `<scratch>\media`, `<scratch>\bootbits`,
   all emptied first. **Refuse a scratch path inside the workspace or inside the
   repository** — a build that writes into the share it is reading is how a
   deployment share gets a `mount` folder in it forever.
5. Copy `winpe.wim` → `<scratch>\<name>.wim`.
6. Copy the ADK `Media` tree → `<scratch>\media`, and create
   `<scratch>\media\sources`.
7. `MountImage(<scratch>\<name>.wim, 1, <scratch>\mount)`.
8. For each component row, in order: `AddPackage(cab)`, then
   `AddPackage(languageCab)` when it is not empty. **The language pack goes
   immediately after its component**, which is DESIGN 5.1's rule and SPIKES S1's
   verified sequence.
9. `SetScratchSpace(mount, workspace.BootImage.ScratchSpaceMB)`.
10. Drivers: when `bootImage.drivers` names a group and
    `Drivers\<group>` exists, `AddDriver(mount, <that path>, $true)` and record
    what came back. When it names a group that does **not** exist: `Write-Warning`
    naming the group and the path, and continue. M5 owns the driver store; a boot
    image build must not be blocked by it. When it names nothing: no call at all.
11. Stage the engine, through `IFileSystem`, into the mount:
    - the module → `<mount>\HDT\Modules\Hephaestus` (from the running module's
      `ModuleBase`, so what ships is what is loaded — **excluding `Payload\`**,
      which is staged separately below);
    - `powershell-yaml` → `<mount>\HDT\Modules\powershell-yaml`, resolved with
      `Get-Module -ListAvailable` and **refused with a named error when absent**,
      because SPIKES S9.1 makes it the dependency the engine rests on in WinPE;
    - `Payload\Start-HDTDeployment.ps1` → `<mount>\HDT\Start-HDTDeployment.ps1`;
    - `Payload\Start-HDTResume.ps1` → `<mount>\HDT\Start-HDTResume.ps1`, because
      the full-OS leg is staged from the boot image to the target.
12. Write `<mount>\HDT\bootstrap.json` in the shape 05-03 defined and reads.
    With `-PromptForCredential`: `promptForCredential: true` and **no**
    `credential` block. Without it: the username from `workspace.yaml` and the
    protected secret from `Get-HDTShareCredential`, and a **refusal** with a
    named error when `workspace.yaml` declares a credential and no secret has
    been written — "run `Set-HDTShareCredential` or build with
    `-PromptForCredential`".
13. Write `<mount>\Windows\System32\startnet.cmd` from `Get-HDTStartnetScript`.
14. `extraContent`: for each entry, resolve the source under the workspace,
    refuse a destination that escapes the mount, and copy. Record each in the
    manifest.
15. `Test-HDTShareAcl` on the workspace for the credential's identity, and
    `Write-Warning` **once per finding** at `Warning` or above. Never fails the
    build (DESIGN 6.3 says warn loudly).
16. `DismountImage(mount, $true)`; then
    `ExportImage(<scratch>\<name>.wim, 1, <workspace>\Boot\<name>.wim)`;
    then **copy that exported file** to `<scratch>\media\sources\boot.wim`.
    *That copy is the whole of DESIGN 6.1.1.* One file, two homes, same bytes —
    the ISO is not built from a second export.
17. Unless `-SkipIso`: `New-HDTBootIso -MediaRoot <scratch>\media
    -Path <workspace>\Boot\<name>.iso -Firmware <…> [-NoPromptForKey]`.
    Then write `<workspace>\Boot\<name>.manifest.json`, **last**, so a manifest
    that exists describes a build that finished.

Returns one row: `WimPath`, `WimSha256`, `WimSizeBytes`, `IsoPath`, `IsoSha256`,
`IsoSizeBytes`, `ManifestPath`, `ComponentCount`, `DriverCount`, `DurationSecond`,
`Skipped` (`[string[]]`).

### The manifest — DESIGN 5.1's answer to boot image drift

`<workspace>\Boot\<name>.manifest.json`, built by
`New-HDTBootImageManifest` (private, pure — it is handed everything it records,
so it can be asserted without a build):

```json
{
  "schemaVersion": 1,
  "buildId": "…", "builtUtc": "…", "builtOn": "LAP-AMMSO01",
  "engineVersion": "0.1.0", "workspaceId": "HDT-LAB",
  "architecture": "amd64", "language": "en-us",
  "adk": { "root": "…", "oscdimg": "…", "winpeWim": "…", "winpeWimSha256": "…" },
  "optionalComponents": [ { "order": 1, "name": "WinPE-WMI", "cab": "…",
                            "languageCab": "…", "required": true } ],
  "drivers":  [ { "inf": "…", "provider": "…", "version": "…", "date": "…" } ],
  "payload":  [ { "destination": "\\HDT\\Modules\\Hephaestus",
                  "source": "…", "fileCount": 0, "sizeBytes": 0 } ],
  "extraContent": [ { "source": "…", "destination": "…", "fileCount": 0 } ],
  "startnet": "…the exact text written…",
  "credential": { "username": "…", "embedded": true, "promptForCredential": false },
  "artifacts": {
    "wim": { "path": "…", "sha256": "…", "sizeBytes": 0 },
    "iso": { "path": "…", "sha256": "…", "sizeBytes": 0,
             "firmware": "UEFI", "noPromptForKey": true, "skipped": false },

```

**`credential` never carries the secret**, and a test greps the serialised

`sources\boot.wim` in the media the ISO was built from, and
**`isoBootWimSha256 === artifacts.wim.sha256`** is DESIGN 6.1.1 written into the
artifact rather than only asserted in a test — so an operator holding a manifest
can check it themselves.
