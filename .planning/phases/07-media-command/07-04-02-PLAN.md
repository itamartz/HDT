<evidence>
Read these before writing anything.

**`Get-HDTConsoleRemoval.ps1`'s `switch ($Kind)`** is one `$shape` hashtable
per kind - `Noun`, `Title`, `Command`, `Parameter`, `Goes`, `IdName`,
`UsedFormat` - composed into one question by code every kind already shares.
Add `'Media'` to the `-Kind` `ValidateSet` and a case:

```
'Media' {
    @{
        Noun      = 'media definition'
        Title     = 'Remove Media'
        Command   = 'Remove-HDTMedia'
        Parameter = 'WorkspaceRoot'
        Goes      = 'media.yaml and the ISO beside it, when the ISO is inside the folder'
        IdName    = 'Id'
        UsedFormat = ''
    }
}
```

`UsedFormat` stays empty - nothing on this share DEPENDS on a media item the
way a sequence depends on an application or an image; a media item is a leaf,
projected FROM the share, never referenced BY anything on it.

**`Remove-HDTMedia -WhatIf` answers a question `UsedBy`/`RequiredBy` was never
built for**: `IsoLeftBehind` - the ISO's path when `-Output` was rooted outside
the media folder, which the command therefore will not delete. That is not the
same shape as "these task sequences use it," so it does not belong in
`Get-HDTConsoleRemoval`'s generic composer. **Compose it in the click handler
instead**, appended to `$ask.Question` after `Get-HDTConsoleRemoval` returns it
- see task 1.

**`removeApplication.Add_Click` in `New-HDTConsoleView.ps1` (~line 1979) is the
shape to copy**: refuse-first via `Get-HDTConsoleRemoval -Kind 'Application'`
(named row check), then `Remove-HDTApplication ... -WhatIf` to learn the
consequences, then `Get-HDTConsoleRemoval` again WITH those consequences to get
the final `$ask`, then `[System.Windows.MessageBox]::Show` with
`YesNo`/`Warning`/default-`No`, then the real
`Remove-HDTApplication ... -Confirm:$false` only on `Yes`, then
`& $rebuildTree` unconditionally. Media's shape is the same skeleton with
`Remove-HDTMedia`'s own `-WhatIf` answer (`Id`, `Path`, `IsoLeftBehind`) in
place of `UsedBy`/`RequiredBy`.

**Remove is offered on a media ITEM and never on the category** - unlike
Update Media Content, which the design deliberately puts on both rows because
building is unambiguous even with several items and the category resolves to
"the only one." Removing the category would have to mean removing every media
definition on the share at once, which is not the press anybody is making by
right-clicking a branch. Build the guard from `$chosen.Kind -eq 'Media'` alone,
the same way `$isApplication` (never `$isAppCategory`) gates
`$removeApplication`.

<design_decisions>
**1. Remove is on the item, never the category** - see evidence. This is the
opposite of Update Media Content's rule and is called out explicitly so nobody
"fixes" it into matching.

**2. The ISO-left-behind warning is composed in the handler, not taught to
`Get-HDTConsoleRemoval`.** Giving the generic composer a fourth shape of
consequence for one kind that is the only one with it is a wrong abstraction;
appending one sentence in the one handler that needs it is not.

**3. Documentation correction is amend-in-place, not rewrite.** Each of the
four spots gets the smallest edit that makes the sentence true again, with a
dated note the way this repository's other reversed deferrals read (see
ROADMAP's "UN-DEFERRED on 2026-09-03" two paragraphs above the line being
fixed).
</design_decisions>
