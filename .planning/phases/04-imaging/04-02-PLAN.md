### `Select-HDTTargetDisk` — the refusal

```
Select-HDTTargetDisk -Disk <object[]> [-Partition <object[]>] [-Volume <object[]>]
                     [-DiskNumber <int>] [-MinimumSizeByte <long>]
                     [-ProtectDriveLetter <string[]>] [-AllowExistingData]
  -> the single disk row, or a terminating error
```

Every exclusion is evaluated for **every** disk and recorded with a reason, so
the error can print the whole table. Two classes of exclusion:

| # | Rule | Excludes | Overridable by `-DiskNumber`? |
|---|---|---|---|
| 1 | `IsSystem` or `IsBoot` | the disk this machine is running from | **NO — never** |
| 2 | holds a volume whose letter is in `-ProtectDriveLetter` | the disk carrying the workspace, the media or the log | **NO — never** |
| 3 | `IsReadOnly` | a disk that cannot be written | **NO** |
| 4 | `IsOffline` | a disk HDT cannot partition without onlining it, and `IDiskService` has no way to online one | **NO** |
| 5 | not `RAW` **and** carries a volume with a file system, without `-AllowExistingData` | a disk with data on it | no — the sequence says `wipe: true` instead |
| 6 | `BusType -eq 'USB'` | the stick the technician booted from | yes, with a warning |
| 7 | `SizeBytes -lt MinimumSizeByte` (default 60 GB) | a disk too small to hold Windows | yes, with a warning |

Then:

- **`-DiskNumber` given.** Unknown number → `HDTConfigurationError` listing the
  numbers that exist. Excluded by 1–5 → `HDTUnsafeTargetError` naming the rule in
  a sentence an administrator can act on ("disk 0 is the disk this machine
  booted from"). Otherwise it is returned, with a `Warning` for 6 or 7.
- **No `-DiskNumber`.** Exactly one survivor → return it. **Zero** →
  `HDTNoTargetDiskError`, listing every disk and its reason. **Two or more** →
  `HDTAmbiguousTargetError`, listing the candidates and saying that
  `diskNumber:` on the step names one. *This is the sentence that stops a
  toolkit from wiping a technician's second drive.*

The three new error ids are added to `Get-HDTFailureClass` as `Configuration`,
so a refusal ends the run instead of being retried.

Rule 1 is absolute on purpose. The alternative — trusting `diskNumber:` — means
one wrong number in a YAML file destroys the machine that is running the
sequence, which on a developer's workstation is the developer's workstation.
`-ProtectDriveLetter` is rule 2's mechanism: `DiskPartition` (04-03) passes the
drive letters of the workspace root and the log path, so HDT cannot wipe the
disk it is reading its own instructions from.

### The named layouts (DESIGN 9.1)

```
Get-HDTDiskLayout [-Name <string>] [-Definition <IDictionary>]
  -> the layout, or every layout when -Name is omitted
```

`-Definition` is where a `workspace.yaml` `diskLayouts:` block will arrive: a
mapping of name → layout that **overrides and extends** the built-ins.
DESIGN 9.1 says layouts live in `workspace.yaml`; **that document does not exist
yet** (M4 introduces it for the boot image), so the built-ins live in this
function and the override hook exists so nothing has to be rewritten when it
does. Say exactly that in the summary rather than quietly diverging from 9.1.

The two built-ins:

| `uefi-standard` (GPT) | Size | File system | Label | Letter | GPT type |
|---|---|---|---|---|---|
| System (ESP) | 260 MB | FAT32 | `System` | `S` | created as basic data `{ebd0a0a2-b9e5-4433-87c0-68b6b72699c7}`, **set to** `{c12a7328-f81f-11d2-ba4b-00a0c93ec93b}` after formatting |
| *(MSR)* | *16 MB* | — | — | — | **not planned — `Initialize-Disk` creates it** |
| Windows | remainder | NTFS | `Windows` | `W` | — |
| Recovery | 1 GB, `UseMaximumSize` | NTFS | `Windows RE tools` | `R` | `{de94bba4-06d1-4d40-a16a-bfd50179d6ac}` |

| `bios-standard` (MBR) | Size | File system | Label | Letter | |
|---|---|---|---|---|---|
| System Reserved | 500 MB, **active** | NTFS | `System Reserved` | `S` | |
| Windows | remainder, `UseMaximumSize` | NTFS | `Windows` | `W` | |

The ESP two-step (`createGptType` then `gptType`) is the field recipe: a
partition created directly as an ESP cannot readily be given a drive letter to
format through. **Record it as unverified-by-code** — 04-04's integration task is
where it first runs, and if `Set-Partition -GptType` after `Format-Volume` does
not behave, the finding goes into SPIKES.md and the layout changes, not the test.

```
New-HDTDiskLayoutPlan -Layout <object> -DiskSizeByte <long>
                      [-MinimumWindowsSizeByte <long>]   # default 20GB
  -> [object[]] ordered rows:
     Order, Role, SizeByte, UseMaximumSize, FileSystem, Label, DriveLetter,
     GptType, CreateGptType, IsActive
```

The arithmetic, which is the whole point of the function:

```
uefi-standard:  windows = DiskSizeByte - 260MB - 16MB(MSR) - 1GB(recovery) - 1MB(alignment)
                recovery row carries UseMaximumSize, so the slack lands there
bios-standard:  windows = UseMaximumSize after a 500MB system partition
```

A disk where `windows` falls below `-MinimumWindowsSizeByte` is a terminating
`HDTConfigurationError` naming the disk size and the shortfall — not a plan with
a negative partition in it.

```
Resolve-HDTDiskLayoutName -Variable <IDictionary> [-Layout <string>]   (private)
  -> 'uefi-standard' | 'bios-standard' | the pinned name
```

Precedence, highest first: the step's `layout:` property → the `HDTDiskLayout`
variable (DESIGN 3.2's HDT-specific addition) → firmware, `HDTIsUEFI` true
meaning `uefi-standard`. A pinned name that no layout defines is a terminating
error listing the names that exist.

### `Resolve-HDTImageIndex` (DESIGN 9.2)

```
Resolve-HDTImageIndex -Image <object[]> [-Index <int>] [-Name <string>]
                      [-Edition <string>] [-DefaultIndex <int>]
  -> the single image row, or a terminating error
```

- `-Index`: must exist, else `HDTConfigurationError` listing the indices present.
- `-Name`: case-insensitive **exact** match first; if none, a wildcard match.
  Two matches → `HDTAmbiguousImageError` naming both.
- `-Edition`: case-insensitive match on `Edition`, same ambiguity rule.
- Several of `-Index`/`-Name`/`-Edition` together: all must agree; a
  contradiction is a configuration error naming both requests.
- None given: one image → that image; otherwise `-DefaultIndex`; otherwise
  `HDTAmbiguousImageError` listing every index and name.

Proven against 04-01's real captures: `win11-ltsc-2024-install.json` (index 1 is
Windows 11 Enterprise LTSC, index 2 the N edition — so `-Name 'Windows 11
Enterprise LTSC'` must **not** match the N edition by accident) and
`ws2025-std-install.json` (four indices, two of which differ only by "Desktop
Experience" — the case that makes exact-before-wildcard matter).

                          [-Name <string>] [-Description <string>] [-Copy]

- The destination is **always** `Get-HDTWorkspacePath -Kind OperatingSystems
  -ChildPath $Id`. No literal `'OperatingSystems'` appears anywhere.
- The image list is read from the WIM through `IImageService.GetImageInfo` — a
  catalog whose indices were typed by hand is a catalog that lies.
- `-Copy` copies the source tree in through `Copy-HDTContentTree` (private:
  `GetChildItem` walk + `CreateDirectory` + `CopyItem`, ordered, no recursion
  into itself). Without `-Copy` the tree is registered in place and `sourcePath`
  is recorded as given. Copying 4 GB is a real operation, so `-Copy` is opt-in.
- `SupportsShouldProcess`: writing into a workspace is a state change (DESIGN
  15.2). Overwriting an existing `os.yaml` needs `-Force`.
- `Clock` is mandatory, for the same reason 03-01 made it mandatory everywhere:
  the only default is a real clock reading inside engine code.

**The content provider is deliberately not built here.** DESIGN 6 abstracts
content access behind `Resolve-Content` / `Copy-Content` / `Test-Content`, and
M4 ships the `Smb` and `Local` providers. Until then `Get-HDTOperatingSystem`
resolves an image path from the workspace root it is given, which is exactly what
a provider would return for `Local`. The seam is the resolved path, so when M4
lands, `ApplyImage` changes from "ask the catalog" to "ask the provider" and no
step logic moves. Record this in the summary so M4 knows where the seam is
rather than rediscovering it.
