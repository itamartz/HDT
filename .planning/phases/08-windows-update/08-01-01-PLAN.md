<objective>
Raise the lab memory budget from 12 GB to 32 GB, put the number in one place, and
stop counting VMs the harness did not create.

**Nothing else in phase 08 can be tested until this is done.** The running set is
`HDT-WDS-01` (4 GB) + `HDT-WSUS-01` (8 GB) = 12884901888 bytes, which is exactly
the current cap, so `New-HDTLabVirtualMachine` refuses to create any target VM at
all and the phase's E2E cannot run. Verified on this host on 2026-09-06:

```
Name          State MemGB Startup Notes
HDT-WDS-01  Running     4       4
HDT-WSUS-01 Running     8       8
```

Both `Notes` fields are empty, which is what makes the marker design work with
nothing to maintain.

Purpose: three changes decided by the user on 2026-09-05.

  (a) **Raise the cap** from 12 GB (12884901888) to 32 GB (34359738368). The host
      has 63.7 GB.
  (b) **One source of truth.** The byte value is currently hardcoded in SIX
      places — `New-HDTLabVirtualMachine.ps1` plus five `tests/e2e/*.E2E.Tests.ps1`
      files that each re-implement the same running-total check inline. Put it in
      one command, have every caller ask, and add a contract test that asserts no
      other file carries the number. CLAUDE.md rule 8, tested against the SET —
      or copy seven appears next phase.
  (c) **Infrastructure VMs stop counting**, and WITHOUT a name list. CLAUDE.md is
      explicit: "the rule is the `HDT-*` prefix, not a list of names — a name list
      rots, and this one did." So `New-HDTLabVirtualMachine` **stamps a marker
      into the `Notes` field** of every VM it creates, and the budget counts only
      stamped VMs. `HDT-WSUS-01` and `HDT-WDS-01` were not created by the harness,
      so they fall out of the budget by construction.

  Bonus safety, worth taking: **`Remove-HDTLabVirtualMachine` refuses an unstamped
  VM**, so teardown can never touch the WSUS or WDS server even though both match
  `HDT-*`.

Output: five new HDTTestTools commands, two rewritten helpers, three test files,
five E2E files wired to the shared check, and five prose surfaces updated.
</objective>

**The tests pass hand-made VM rows, never a real VM.** `Get-HDTLabMemoryUse`
takes an optional `-VirtualMachine [object[]]`; when it is supplied the function
makes NO Hyper-V call, which is what makes every assertion above runnable in the
normal unit suite on a machine with no Hyper-V. A row is a `[pscustomobject]` with
`Name`, `State`, `MemoryAssigned`, `Notes` — the four properties `Hyper-V\Get-VM`
returns and the ones the real path reads.

Now the implementations, each with comment-based help:

1. **`Get-HDTLabMemoryBudget`** — pure, no parameters, no Hyper-V. Returns
   `[pscustomobject] @{ CombinedByte = [long] 34359738368; PerVmByte = [long] 8589934592;
   CombinedText = '32 GB'; PerVmText = '8 GB' }`.
   **THIS IS THE ONLY FILE IN THE REPOSITORY THAT MAY CARRY EITHER BYTE VALUE.**
   Say so in the help, and say why: the number used to live in six places, five of
   which re-implemented the same running total, and raising it meant finding all
   six. Note the host figure (63.7 GB) as the reason 32 is safe and 64 is not.

2. **`Get-HDTLabVmStamp`** — pure. Returns the marker written into `Notes`.
   Use exactly:
   `'Created by HDT tests/helpers/HDTTestTools. This VM is disposable and counts against the lab memory budget.'`
   Two jobs in one string, and the help must say both: it tells a human reading
   Hyper-V Manager that the VM is safe to delete, and it tells the harness which
   VMs are its own. A UUID would do the second job and not the first.

3. **`Test-HDTLabVmStamped -Note [string]`** — pure, `[AllowNull()]`,
   `[AllowEmptyString()]`. Returns `$true` when the note contains the stamp
   (`-like ('*{0}*' -f (Get-HDTLabVmStamp))`, case-insensitive). `$null` and empty
   are `$false`. The help says why it is a substring test and not equality: an
   operator who adds a line to a VM's notes must not silently drop it out of the
   budget or, worse, out of teardown.

4. **`Get-HDTLabMemoryUse [-VirtualMachine [object[]]]`** — returns
   `[pscustomobject] @{ AssignedByte = [long]; Counted = [string[]]; Ignored = [string[]] }`.
   With `-VirtualMachine` it filters the rows it was given; without it, it calls
   `@(Hyper-V\Get-VM -Name 'HDT-*' -ErrorAction SilentlyContinue)` — name-filtered,
   never an unfiltered pipeline. A row counts when `State -eq 'Running'` AND
   `Test-HDTLabVmStamped -Note ([string] $_.Notes)`. `MemoryAssigned` is the
   correct property (SPIKES S23, line 712 of `.planning/SPIKES.md`).
   **The help carries the whole design rationale for the stamp**, because this is
   where somebody will come looking: a name list rots (CLAUDE.md says so, and the
   E2E lab-safety assertion already rotted once by comparing two empty arrays and
   passing while checking nothing), so membership of the budget is decided by what
   the harness DID, recorded at creation, and never by what anybody remembered to
   write down. `HDT-WSUS-01` and `HDT-WDS-01` fall out by construction. Say that
   in prose — and do not name them in a comparison.

5. **`Assert-HDTLabMemoryBudget -MemoryByte [long] -Name [string] [-VirtualMachine [object[]]]`**
   — the check every caller uses. Throws when `$MemoryByte -gt PerVmByte`, and
   throws when `(Get-HDTLabMemoryUse).AssignedByte + $MemoryByte -gt CombinedByte`.
   Both messages quote the numbers from `Get-HDTLabMemoryBudget` — never a literal
   — name the VM being started, list the counted VMs, and cite
   "PROJECT.md, 'Hyper-V lab safety rules', rule 4". The combined-budget message
   also says how many running `HDT-*` VMs were IGNORED and why, because a
   technician who sees "0 bytes already assigned" while Hyper-V Manager shows two
   running VMs will otherwise think the check is broken. Returns nothing on
   success. `-VirtualMachine` is passed straight through to `Get-HDTLabMemoryUse`
   and exists only so the unit tests above can run without Hyper-V.
