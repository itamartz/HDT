### The loop

```
Invoke-HDTTaskSequence -Sequence <object> -Context <object>
                       [-State <object>] [-StatePath <string>] [-MirrorStatePath <string>]
                       [-StepType <object[]>] [-StatusPath <string>] [-LogDestination <string>]
    -> [pscustomobject] @{
           Status      Succeeded | Failed | RebootPending
           State       the state document as it stands
           Result      [object[]] one per step attempted, in order
           FailedStep  the flattened step that ended the run, or $null
       }
```

`SupportsShouldProcess`, because it runs steps that change machines.

The algorithm, in order. Every branch below is a test.

```
run.start                      (log, then Write-HDTStatus)
phase.change                   (only when $Context.Phase differs from $State.phase)
try {
    $registry = discover step types once, or use -StepType
    for ($i = $State.stepIndex; $i -le $Sequence.Step.Count; $i++) {

        $step = $Sequence.Step[$i - 1]
        $Context.SetStep($i, $step.Name, $step.Type)
        $Context.Attempt = 1
        $Context.Log.SetStep($i, $step.Name, $step.Type, (Get-HDTStepLogName $i $step.Name))

        # 1. already done on a previous leg
        if state.step[$i].status in Completed, Skipped -> step.skip 'completed on leg N'; continue

        # 2. interrupted on a previous leg
        if state.step[$i].status is Running:
              if $step.Resumable -> log Warning 'resuming an interrupted step'; fall through
              else               -> FAIL THE RUN, 'step {n} '{name}' was interrupted and does not declare resumable: true'

        # 3. phase filter
        if -not (Test-HDTStepRunInPhase -RunIn $step.RunIn -Phase $Context.Phase)
              -> Skipped, step.skip, reason names both; continue

        # 4. group conditions, outermost first
        foreach ($c in $step.GroupCondition) {
            if -not (Test-HDTStepCondition -Condition $c.Condition -Variable $Context.Variable)
                  -> Skipped, step.skip, reason names THE GROUP; continue outer
        }

        # 5. the step's own condition
        if -not (Test-HDTStepCondition -Condition $step.Condition ...)
              -> Skipped, step.skip, reason names the condition; continue

        # 6. applicability
        if -not (Test-HDTStepApplicable -Step $step -Context $Context -StepType $registry)
              -> Skipped, step.skip, 'not applicable'; continue

        # 7. run it
        Update-HDTRunStateStep -Status Running ; Save-HDTRunState     <- the checkpoint that
                                                                        makes case 2 detectable
        step.start (log)
        $result = Invoke-HDTStepAttempt -Step $step -Context $Context -StepType $registry

        Update-HDTRunStateStep with the outcome, duration, exit code, message
        Save-HDTRunState

        switch ($result.Status) {
          'Completed'       -> step.complete ; continue
          'RebootRequested' -> the reboot ceremony below ; return RebootPending
          'Failed'          -> step.fail
                               if $step.ContinueOnError -> log Warning 'continuing'; continue
                               else -> FAIL THE RUN
        }
    }
    Status = Succeeded
} catch {
    Status = Failed ; log step.fail or run-level failure with the exception
} finally {
    $State.status = Succeeded | Failed | Running(for RebootPending)
    Save-HDTRunState
    run.end (log, with the counts) ; Write-HDTStatus
    Copy-HDTLog when -LogDestination was given
    if Status is Succeeded or Failed:
          Clear-HDTAutoLogon        <- DESIGN 4.5.2: teardown is a failsafe, not a step
    if Status is RebootPending:
          NOTHING is torn down      <- the machine must stay armed across the reboot
}
```

**`PauseOnError`** (DESIGN 4.3) is read from `$State.pauseOnError`. When set and a
step fails terminally, the loop logs at `Error` that the run is paused, writes the
status heartbeat, and **returns** with `Status = Failed` and the state loaded —
it does not call `Read-Host` or start a nested prompt. Dropping to a live prompt
is the responsibility of the caller (`Start-HDTDeployment.ps1`, phase 05); an
engine that blocks on input cannot be unit tested and would hang CI. Say so in
the help.

### The reboot ceremony — the order is the design

On `RebootRequested`, in exactly this order:

1. mark the step `Completed`, which advances `stepIndex` to the next step;
2. **`Save-HDTRunState`** — the durable checkpoint;
3. take the deployment password from `$State.deploymentPassword`, generating one
   with `New-HDTDeploymentPassword` and storing it there on the first reboot;
4. `Set-HDTAutoLogon -RemainingLeg (1 + the number of remaining steps of type Restart)`;
5. **`Save-HDTRunState`** again, so `autoLogon.armed` is durable;
6. `reboot.arm` log record and `Write-HDTStatus`;
7. `$Context.Service.Power.Restart($delaySecond)`;
8. return `RebootPending`.

**Why save before arming.** If arming succeeds and the save then fails, the
machine reboots, autologons, and resumes at the *old* index — re-running the
`Restart` step, which reboots again: an infinite loop that needs a technician and
a boot menu. If the save succeeds and arming then fails, the machine reboots and
simply stops at the logon screen: stuck, but safe and diagnosable. Between a loop
and a stop, choose the stop. This ordering is asserted from the 03-01 journal, not
inferred.

`RemainingLeg` is a **bound, not a prediction**: a `CommandLine` step returning
3010 can add a leg nobody counted. Every arm re-sets the count, so the bound is
refreshed on each reboot. Say this in the help rather than implying the number is
exact.

### Retry, backoff and timeout — `Invoke-HDTStepAttempt`

```
Invoke-HDTStepAttempt -Step -Context -StepType -> the step result, plus:
    Attempt      the attempt the result came from
    DurationMs   measured with $Context.Service.Clock
    TimedOut     bool
    FailureClass Transient | Configuration | Environment
```

- Attempts run from 1 to `1 + $Step.Retry.Count`.
- The delay before attempt N is `DelaySecond` for `fixed`, and
  `DelaySecond * 2^(N-2)` for `exponential`, taken through
  `$Context.Service.Clock.Sleep()` so no test waits.
- **A `Configuration` failure is never retried.** Retrying bad authoring wastes a
  deployment's time and hides the real message. Classification comes from
  `Get-HDTFailureClass`:

  | Signal | Class |
  |---|---|
  | `FullyQualifiedErrorId` starting `HDTConfigurationError` | `Configuration` |
  | `System.IO.*`, `System.ComponentModel.Win32Exception`, a timeout | `Environment` |
  | anything else, including a `Failed` step result with an exit code | `Transient` |

- `timeoutMinutes` is passed to the step (only `CommandLine` can enforce it, via
  `IProcessService`), **and** measured by the loop: if the elapsed time from the
  clock exceeds it, the result becomes `Failed` with `TimedOut = $true` even when
  the step returned success.
  **State the limitation in the help and the summary:** HDT does not preempt a
  synchronous step. A step that hangs in-process hangs the sequence, exactly as
  MDT's does. Running steps in a child runspace to make timeouts pre-emptive is a
  post-v1 idea, and `ForEach-Object -Parallel` is not available to us anyway.
- An exception thrown by a step is caught **here**, not by `Invoke-HDTStep`, and
  becomes a `Failed` result carrying the message and the class.

### `Test-HDTStepRunInPhase` and `Get-HDTStepLogName`

```
Test-HDTStepRunInPhase -RunIn <WinPE|FullOS|Any> -Phase <WinPE|FullOS> -> [bool]
Get-HDTStepLogName -Index <int> -Name <string> -> '003-Apply-OS.log'
```

The log name is DESIGN 4.4's numbered per-step file: the index zero-padded to
three digits, then the step name with every character outside `A-Za-z0-9._-`
replaced by `-`, collapsed, trimmed, and truncated to 40 characters. A step named
`Apply OS (index 3)` becomes `003-Apply-OS-index-3.log`. Numbering by execution
order is what makes the directory listing tell a technician where the deployment
stopped.

### `Test-HDTTaskSequence` — authoring-time checks the schema cannot do

```
Test-HDTTaskSequence -Sequence <object> [-StepType <object[]>] -> [pscustomobject[]]
    one record per finding: Severity (Error|Warning), Step, Message
```

- `Error`: a step whose `type` no loaded module implements — with the known types
  listed.
- `Warning`: a `runIn: WinPE` step after a `Restart` in a sequence that has no
  way back to WinPE; a step referencing a `%Var%` that no rule, sequence variable
  or earlier `SetVariable` step could supply; `continueOnError: true` on a
  `Restart`.
- It returns findings rather than throwing, because it is a lint, and the console
  (M8) will surface it inline.

### `Start-HDTResume.ps1` — the RunOnce payload

`src/Hephaestus/Payload/Start-HDTResume.ps1`. Not a module file: the loader only
dot-sources `Private/` and `Public/`, so this is staged to `C:\HDT\` and run by
the `RunOnce` entry `Set-HDTAutoLogon` writes. It:

1. imports the module from `C:\HDT\Modules\Hephaestus` (parameterised with
   `-ModulePath` so a test can point it elsewhere);
2. builds the real services;
3. calls **`Invoke-HDTBootReconciliation` first, before anything else** — DESIGN
   4.5.2;
4. exits 0 when the reconcile said `Teardown`;
5. otherwise rebuilds the log context from the state's `seq` and `runId`,
   re-imports the sequence, and calls `Invoke-HDTTaskSequence -State $state`.

It is a script, so it is tested by **parsing and inspecting** it rather than by
running it: the assertions are that it exists, parses under both engines, calls
the reconcile before the loop, and passes `-State`. Running it for real belongs to
phase 04's integration layer, where there is a machine to reboot.
