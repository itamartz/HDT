<objective>
Put media on screen. A `Media (n)` node in the share tree beside Applications and
Operating Systems, its items as rows showing the selection profile, the output
path and the last build, and an **Update Media Content** action that runs
`Update-HDTMediaContent` through the progress window the boot image build already
uses.

Purpose: MDT's Deployment Workbench has a Media node under Advanced
Configuration with exactly this action on it. Plan 02 built the command; a
command an administrator can only reach from a prompt is half a feature, and
this repository has shipped that one before — the Windows Updates feature had a
tree node, a detail pane, an import dialog and a host method, and right-clicking
any of it did nothing, because none of its kinds were written down in
`Get-HDTConsoleTreeMenuRow`.

Output: a Media category, its rows, one menu item, one wired action, and a
photograph of the window proving it.
</objective>

<evidence>
Read these before writing anything.

**`Get-HDTConsoleShareNode.ps1`** builds seven categories the same way and the
selection-profile block at line ~829 is the one to copy: a `Category` node at
`Depth 2` with `-Name`, `-Text 'X (n)'`, a named `-Icon`, a `-Command` string and
fields; item rows at `Depth 3`; **every row added to BOTH `$node` (the flat
reading, in display order) and its parent's `.Children` (what the window
expands)**. Building them separately is how the two come to disagree — the file
says so.

**`Get-HDTConsoleIcon.ps1`'s `-Kind` `ValidateSet` is closed on purpose** and a
kind not in it throws. It needs `Media`. The glyph table's comments record why
each picture was chosen and why several were changed; write the same kind of
sentence for this one rather than picking an emoji.

**`Get-HDTConsoleTreeMenuRow.ps1`** carries `$offers`, "EVERY KIND THAT HAS
SOMETHING ON THE MENU", and its own comment records the Windows Updates
half-feature above. A `Media` kind that is not in that list is a row whose
right-click does nothing, and **only a person with a mouse can see it** — which
is how it reached one.

**`Show-HDTBuildProgressWindow`** already takes `-Command`, `-Argument`,
`-StringPage` and `-LogFile`. The generic dispatch was built on 2026-08-27 when a
2.38 GB driver import froze the console for 86 seconds: `$Command` is a **name**
and `$Argument` a **plain hashtable**, both deliberately, because they cross a
runspace boundary where a scriptblock would arrive bound to a session state the
far side cannot invoke. **So this plan writes no runspace code at all** — it
passes a different command name to machinery that already exists.

**`New-HDTConsoleHost.ps1`'s handler rules**, enforced by
`tests/contract/ConsoleSurface.Contract.Tests.ps1`: a handler reaches a private
function only through `Get-HDTHandlerCall` (`$call`), never by name; `$call` must
be declared in every scope that names it; no colon-bound switch through it; and
`GetNewClosure` only where the sweep can read it. Read the four `It`s in that
file before touching a handler.

**Console wiring IS testable in Pester** — `tests/unit/ConsoleTreeMenuWiring.Tests.ps1`
builds a real WPF view with no desktop, `RenderOptions.ProcessRenderMode =
'SoftwareOnly'`, and right-clicks rows. The blocker was only ever `ShowDialog`.

**MEMORY, and it costs an afternoon each time:** probe the console from Windows
PowerShell 5.1 with a **clean `PSModulePath`** — a pwsh-7-inherited path poisons
a 5.1 child and every HDT window dies before it draws. Hand the tree its ROOTS
(`Depth -eq 0`) and not the flat list, or every node draws twice and it looks
exactly like a duplication bug in the tree builder.
</evidence>

<design_decisions>
Four calls, stated once.

**1. One action on the menu, and the absence of the others is deliberate.**
`Update Media Content` is what MDT's Media node offers and what the phase scope
names. **New Media and Remove Media are NOT on the menu in this phase** — they
are `New-HDTMedia` and `Remove-HDTMedia` at a prompt. This is written down here,
and it goes in the summary, because an unexplained gap between the command set
and the menu reads as a half-feature. It is a deferral, not an oversight.

**2. Both media rows offer it — the category and an item under it** — which is
the rule the boot image and selection profile rows already follow, for their
reason: it is one action on one thing, and which of the two somebody right-clicks
when there is one media definition is not worth being wrong about. The category
row runs it for the **only** media when there is exactly one and is disabled
otherwise; an item row runs it for that item.

**3. The category counts what it holds, like every other one.** `Media (2)`. A
share with none shows `Media (0)` and a `(none)` row — never a missing branch,
which reads as "this share cannot do media".

**4. The row's fields are the three questions somebody opens the branch to ask:**
which profile, where the ISO goes, and when it was last built. `Last build` reads
`LastBuildUtc` off the object plan 02's `Get-HDTMedia` returns, and shows
`(never built)` when it is empty — the honest answer, and the one that tells an
administrator the action on this row is the one they want.
</design_decisions>
