<objective>
`Invoke-HDTWindowsUpdateStep` — DESIGN 10.1's online, full-OS Windows Update step,
with its multi-pass loop.

```yaml
- name: Windows Update
  type: WindowsUpdate
  server: "%HDTWSUSServer%"        # optional; omit for Windows Update / policy default
  categories: [SecurityUpdates, CriticalUpdates, UpdateRollups]
  exclude: ["*Preview*", "KB5001234"]
  maxPasses: 3
  continueOnError: true
```

Purpose: **multiple passes are the point.** Installing one update supersedes or
reveals another, so the step loops — search, install, reboot if required, search
again — until a pass returns nothing applicable or `maxPasses` is hit. A
single-pass Windows Update step is the classic MDT mistake that leaves machines
half-patched, and PSD's own `PSDWindowsUpdate.ps1` is single-pass: read it for the
COM mechanism and not for the shape.

Output: the step, three pure decision helpers, and an authoring-time refusal that
stops a `WindowsUpdate` step being put where WUA does not exist.
</objective>

Write `Get-HDTFullOsOnlyStepType`'s help in the same voice:

- `WindowsUpdate` is there because the Windows Update Agent COM server does not
  exist in the WinPE image at all. Not "does not work well" — is not present.
- **`InstallRoles`, `EnableBitLocker` and `JoinDomain` are deliberately NOT

is the question the next reader will have.

Three decisions to write into the help, each of which a reader will otherwise
have to guess at:

1. **A KB number is normalised to `KB#####` in one place.** The agent returns
   `KBArticleIDs` WITHOUT the prefix; humans write it WITH one; DESIGN 10.1's
   example `exclude` list mixes `"*Preview*"` and `"KB5001234"` in the same array.
   `Get-HDTUpdateKbNumber` is the one place the two spellings meet.
2. **An exclude entry is a KB number if it looks like one, and a title wildcard
   otherwise.** `KB5001234`, `kb5001234` and `5001234` are KB numbers;
   everything else is matched against the title with `-like`. This is a decision
   and it goes in `Test-HDTUpdateExcluded`, tested, not inferred at the call site.
   Test both readings explicitly — a title match on a bare number would exclude
   half a catalogue by accident, which is what "does not let a bare number match a
   title that merely contains it" is guarding.
3. **A category is matched with the spaces removed.** WUA reports
   `Security Updates`; DESIGN 10.1's YAML writes `SecurityUpdates`; MDT writes
   both. Compare on `ConvertTo-HDTComparableString`-style normalisation — that
   private helper already exists, so use it rather than adding a fourth way to
   compare two strings loosely.

`Select-HDTApplicableUpdate -Update [object[]] -Category [string[]] -Exclude [string[]]`
returns one row per input update: the update, `Applicable [bool]`, and
`Reason [string]` — `'no category filter'`, `'category SecurityUpdates'`,
`'excluded by *Preview*'`, `'no category matched'`. **It never silently drops
anything**, because the step's log has to be able to say why an update the
administrator expected did not install. That is the difference between a log
somebody can act on and one that says "0 updates applicable".

**Then the step.** Copy the structural shape of
`Invoke-HDTInstallRolesStep` — the `$fail` scriptblock writing `step.fail` at
`Error` and returning `New-HDTStepResult -Status Failed`, `Get-HDTStepProperty
-Expand -As Bool|String|Int` for every property, `$Context.Service.GetRequired`
for the service, `Write-HDTLog -Event 'native.exec'` around the work.

Properties, per DESIGN 10.1:

| Key | Type | Default |
|---|---|---|
| `server` | string, variable-expanded | absent — Windows Update / policy default |
| `categories` | string list | absent — every category |
| `exclude` | string list | absent — exclude nothing |
| `maxPasses` | int | **3** |
| `continueOnError` | bool | **true** — and this is a COMMON key the loop owns, not a step property; the step's TEMPLATE writes it, the step does not read it |

`categories` and `exclude` are YAML sequences. **Walk a list element by element
and expand each**, and expand the flat string form through
`Get-HDTStepProperty -Expand`, exactly as `InstallRoles` does for `features` and
`InstallApplications` does for `selection` — both carry a comment saying why, and
both got it wrong first. A list handled only in the flat form makes
`exclude: ['%HDTExcludePattern%']` search for an update whose title is a percent
sign.

**The loop:**

```
pass = <checkpoint>            # _HDTWindowsUpdatePass, 0 on the first leg
while (pass < maxPasses) {
    pass++
    found     = service.SearchUpdate('IsInstalled = 0')
    decided   = Select-HDTApplicableUpdate -Update $found -Category $categories -Exclude $exclude
    applicable = decided where Applicable
    log the whole decided set: what was found, what was kept, what was dropped and why

    if (applicable is empty) { -> Completed, "pass N found nothing applicable" }

    foreach (update in applicable) {
        accept EULA; download if not already downloaded; install; time it; log it
    }

    if (any install asked for a reboot -or service.GetRebootRequired()) {
        checkpoint pass; -> RebootRequested -Reenter
    }
}
-> Completed, "reached maxPasses (N) with updates still applicable" as a WARNING
```

Six things this loop must get right, each of which is a way the feature is
usually broken:

1. **`-Reenter` is not optional.** `New-HDTStepResult -Status RebootRequested
   -Reenter` exists for exactly this shape — phase 07 built it for
   `InstallApplications` hitting a 3010. Without it the engine records the step
   Completed, advances `stepIndex`, and every remaining pass is silently skipped
   while the run reports success. Its help (line ~44) spells this out; read it.
2. **The pass counter is checkpointed into `$Context.Variable`**, not held in a
   local. `_HDTWindowsUpdatePass`, alongside `_HDTWindowsUpdateInstalled` (the KB
   numbers this run has put on, across every leg). `state.json` persists them, the
   leg after the reboot rehydrates them, and the step reads them on entry —
   `Invoke-HDTInstallApplicationsStep` does exactly this with
   `_HDTApplicationInstalled` at lines 133, 315 and 353. Without the checkpoint
   the step restarts at pass one on every leg and `maxPasses` never bounds
   anything.
3. **`maxPasses` bounds the STEP, across legs**, not the leg. That is what the
   checkpoint buys.
4. **Ask the machine as well as the install result.** `InstallUpdate` reports
   `RebootRequired` for the batch; `GetRebootRequired()` reports a pending restart
   from anything, including the servicing stack update that went in first. A
   servicing-stack update that does not set the batch flag but leaves a pending
   restart will make the next search return stale results. Check both.
5. **A failed update does not stop the pass** — record it, go on. The step fails
   only when every update in a pass failed, because at that point another pass
   will do the same thing. `continueOnError: true` then decides whether that
   failure scraps the build, and DESIGN 10.1 says it is the recommended default:
   "Windows Update is the least predictable thing in a sequence, and a failed
   optional update should not scrap an otherwise good build."
6. **Reaching `maxPasses` with work outstanding is a WARNING, not a failure.** The
   machine is more patched than it was. Log it loudly — at `Info`, naming the
   updates still applicable — so an administrator can see the bound was hit rather
   than discovering it from a patch report.

**The log, and CLAUDE.md's rule about it.** Per update, at `Info`: pass number, KB
number(s), title, classification, size, the outcome, the result code AND what that
code means, the HResult on a failure, and the elapsed seconds. Per pass: what the
search returned, what the filter kept and dropped and why, and how long the pass
took. `Debug` is for volume, not for importance — an administrator needs all of
the above to explain a slow deployment, and DESIGN 10.1 says the step logs
per-update timing for exactly that reason.

`Data` on the result carries: `pass`, `maxPasses`, `server`, `searched`,
`applicable`, `installed` (KB numbers, across every leg), `installedThisPass`,
`skippedExcluded`, `skippedCategory`, `failed` (with HResults), `rebootRequired`,
`elapsedSecond`. Keep the two kinds of skip separate for the same reason
`InstallApplications` keeps its two apart: one says the administrator excluded it,
the other says it was not in scope, and merging them loses the answer to "why did
this machine not get that patch".
